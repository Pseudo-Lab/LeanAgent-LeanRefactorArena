# 현재 증명에서 고르는 수정 전략

아래는 후보 생성 지침이다. 어느 변형도 성능 개선이나 컴파일 성공을 보장하지 않는다. 현재 목표·가정·정의와 실제 측정 결과를 보고 채택한다.

| 관찰한 구조 | 시도할 편집 | 확인할 부분 |
|---|---|---|
| 짧은 `apply`/`exact` 연결 | 현재 가정으로 직접 적용하는 증명 구성 | 추론이 더 무거워지지 않는지, 토큰·HB |
| 생성자와 가정으로 닫히는 분기 | 단순 분기를 직접 닫고 자동화에 넘길 목표 축소 | 귀납가정·분기 태그·남은 목표 |
| 중첩 `.elim`·람다 또는 긴 증명항 | 필요한 가정을 꺼내고 생성자로 조립하는 후보와 비교 | 바인더 범위·존재 증인·HB |
| 한 번 쓰는 중간 가설 | 사용 위치에 직접 전달하거나 목표에 재작성 | 삭제 전 사용 위치·의존성·전체 문맥 |
| 여러 곳에서 같은 조건을 증명 | 증명 본문 안에서 공통 조건 한 번 구성 | 재사용 이득과 선언 비용, 인스턴스 범위 |
| 넓은 자동 탐색 또는 반복 대안 | 목표 구조를 먼저 분해하거나 검색 결과를 명시화 | 사용 lemma의 해당 버전 존재 여부, HB |
| `simp` 목록이나 반복 단순화 | 불필요한 원소 삭제, 범위 조정, 짧은 대안 비교 | 국소 simp 집합·타입 추론 변화·모든 버전 |
| 큰 구조의 중복·국소 편집 정체 | 기존 lemma 검색 후 별도 후보에서 전체 증명 경로 재구성 | 원래 명제 유지, 최선 후보 보존, 잔여 시간·예산 |

## 시도 순서

작은 삭제·직접 적용 후보를 먼저 비교하고, 필요한 경우 정리 검색과 더 큰 재작성을 시도한다. 구조를 바꾼 뒤에는 이전에 필요했던 중간 단계가 남았는지 다시 확인한다. 이 순서는 강제된 전술 순위가 아니다. 같은 목표에서 더 나은 근거가 있으면 그 후보부터 측정한다.

후보는 기존 `trial.py`가 받는 `[{"label": "편집 의도", "edits": [["변경 전 구간", "변경 후 구간"]]}]` 형식으로 전달할 수 있다. 변경 전 구간은 정확히 한 번 나타나야 한다. 실패한 후보로 기준 후보를 덮어쓰지 않는다.

LSP·REPL 도구가 있으면 수정 직전 목표와 수정 뒤 진단을 읽는다. 없으면 기존 파일 검사를 사용한다. 도구가 제시한 `simp?`·`aesop?` 결과도 최종 파일에 넣어 재검증할 후보로 다룬다. 해당 tactic이나 lemma가 고정 환경에 실제로 있을 때만 시도한다.

들여쓰기·불릿·`<;>` 변경은 목표 분배를 바꿀 수 있다. 줄 수 절약을 개선량으로 세지 않는다. 텍스트 탐지 결과는 후보 위치이며 Lean 구문 분석이나 검증의 대체물이 아니다.

## 오류 피드백

다음 시도에는 바꾸는 구간, 그 직전 목표·가정, 실제 오류 위치, 필요한 선언의 타입을 제공한다. 로그 전체를 매번 붙이거나 같은 실패 요청을 그대로 재전송하지 않는다. 가져온 선언이 없으면 고정 프로젝트에서 다시 검색하고, API 비용·실행 환경 문제가 나면 증명 수정과 구분해 처리한다.

전역 정책을 고치기 위해 benchmark 실패별 예외를 축적하지 않는다. 한 문제의 수리 이력은 그 문제의 실행 문맥에 보관한다. 정책 개선 절차는 [evaluation.md](evaluation.md)를 따른다.
