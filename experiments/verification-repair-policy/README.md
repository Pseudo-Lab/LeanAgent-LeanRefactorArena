## 1. 연구 질문

같은 모델과 예산에서, 검증 실패의 종류에 따라 다음 행동을 선택하면 최종 증명 개선량이 늘어나는가?

첫 비교는 **남은 목표만 있는 후보를 계속 수리할지, 검증된 최선 후보에서 다시 계획할지**에 한정한다.
진단의 표현, 점수 정보의 제공 시점, 검증 기준은 두 조건에서 같게 둔다.
이 실험은 정상 원본에서 시작하는 리팩터링이다. 원본을 숨기는 손상 증명 복구 실험과 구분한다.

## 4. 비교 조건: 한 행만 바꾼다

조건 이름은 과거 실험의 A1/A2/B1/B2와 구분한다.

| 조건 | 정책 ID | 핵심 동작 |
| --- | --- | --- |
| 고정 수리 | `uniform-repair-v1` | 수리 가능한 실패이면 현재 후보에서 수리한다. |
| 상태별 선택 | `state-aware-v1` | proof_error는 현재 후보에서 수리하고, incomplete는 best에서 재탐색한다. |

`uniform-repair-v1`은 실험용으로 명시한 기준선이다. 현재 main의 모델 자율 행동과 같다고 주장하지 않는다.
이 두 조건만으로 현재 main보다 낫다고 주장할 수도 없다. 그런 주장은 별도 main 조건의 반복 비교가 필요하다.

### 공통 상태 분류

검증기의 원래 결과는 변경하지 않는다. 아래 `policy_state`는 다음 행동을 고르기 위한 별도 값이다.
전체 진단 원문을 먼저 분류하고, 모델에 보낼 길이 제한은 그다음에 적용한다.

| policy_state | 필요한 근거 |
| --- | --- |
| `valid` | 동일 평가기의 컴파일·정책·공리·계측 검사를 통과한 후보 |
| `proof_error` | 타입·구문·미정의 이름·전술 실패 등 구체적인 Lean 오류. 미완성 징후와 함께 있으면 이 상태를 우선 |
| `incomplete` | 검사 자체는 완료됐으며, 명시적인 unsolved-goals 진단만 있고 다른 오류·금지 공리·범위 위반이 없음 |
| `response_rejected` | JSON 계약 또는 허용 proof body 계약을 충족하지 못한 응답 |
| `environment`, `measurement`, `timeout`, `api`, `unknown` | 기존 진단과 원문에 근거한 운영 실패 또는 판정 불가 |

`goals=null`은 수집하지 못했다는 뜻이다. 이를 `goals=[]`나 `incomplete`로 바꾸지 않는다.
명시적 unsolved-goals 진단으로 incomplete를 구분하더라도 native goal/local context 필드는 미수집이면 null이다.
필요한 로그가 없거나 분류가 모호하면 `unknown`이다. 고정 사례에서 분류가 확인되기 전에는 유료 비교를 시작하지 않는다.
InfoTree 수집을 추가한다면 두 조건에 같은 수집기·정보·실행 비용을 적용한다.

### 행동과 우선순위

`best`는 검증된 원본에서 시작한다. 완료된 후보의 검증·선택을 먼저 기록하고, 다음 행동을 아래 표의 위에서부터 결정한다.
따라서 마지막 허용 호출에서 얻은 유효한 개선도 예산 종료나 수리 상한 판정 전에 best에 반영한다.

| 조건 | 고정 수리 | 상태별 선택 |
| --- | --- | --- |
| 호출 예산·전체 실행 한도 도달 | best를 보존하고 종료 | 동일 |
| 환경·계측·timeout·API·원인 불명 | best와 미확정 비용을 보존하고 종료. 자동 유료 재시도 없음 | 동일 |
| `valid` | 갱신된 best에서 개선 계속 | 동일 |
| `response_rejected` | 기존 best에서 다음 요청. 출력 계약 안내를 제공 | 동일 |
| 동일 proof 해시가 재제출됨 | 현재 수리 묶음을 닫고 best에서 재탐색 | 동일 |
| 현재 수리 묶음에서 후속 호출 2회를 이미 사용 | 현재 수리 묶음을 닫고 best에서 재탐색 | 동일 |
| `proof_error` | `repair_current` | `repair_current` |
| **`incomplete`** | **`repair_current`** | **`replan_from_best`** |

첫 실패를 만든 생성 호출은 후속 수리 2회에 포함하지 않는다. 이후 그 실패 후보를 기준으로 요청한 호출은 성공·실패·응답 거절 여부와 관계없이 수리 횟수에 포함한다.
유효 후보, 응답 거절, best 재탐색, 중복 후보, 수리 상한에서 수리 묶음을 닫는다. 다음 독립 실패부터 새 묶음을 연다.
중복 해시는 이 실행에서 이미 제출한 proof bytes를 기준으로 한다. 원본 해시도 비교 집합에 포함한다.
중복을 발견해도 이미 발생한 모델 비용을 취소하지 않는다. v1에서는 평가 캐시를 새로 추가하지 않는다.
반복 오류의 의미적 동일성을 판정하거나 같은 goal이 줄었는지를 비교하는 규칙은 v1에서 제외한다.

`repair_current`는 최신 실패 후보를 수정 기준으로 지정한다. 해당 진단의 오류 또는 남은 목표를 해결하도록 요청한다.
`replan_from_best`는 검증된 best를 수정 기준으로 지정한다. 실패 사실은 유지하되 그 실패 후보를 이어 고치지 말고 다른 증명 경로를 시도하도록 요청한다.
`optimize_best`는 유효한 best에서 추가 개선을 요청한다. 첫 호출도 이 행동으로 시작한다.
수리 상한과 상태별 선택은 새로운 가설이다. 이전 리포트가 위 값이나 전환의 효과를 입증한 것은 아니다.

### 입력 정보 통제

두 조건은 같은 공통 지시, 원본·문맥, best, latest, 최근 후보 수, 진단 필드와 길이 제한, 점수·프로파일 정책을 사용한다.
분류기와 수리 이력 계산기도 같다. 기준선에서도 policy_state를 계산하고 같은 사실을 제공한다.
같은 상태 snapshot이라면 `action`, `base_candidate_sha256`, 행동 지시만 달라질 수 있다.
정책 ID는 원장에 기록하고 모델의 별도 힌트로 쓰지 않는다.
조건이 달라진 뒤 후보·이력·입력 길이가 달라지는 것은 정책의 결과이며 비용에 포함한다.
행동 전환을 요청했다는 사실과 모델이 실제 증명 구조를 바꿨다는 사실은 구분해 보고한다.
점수 숨기기, 유형별 진단 요약, 문맥 삭제, 이름 검색, 로컬 golf는 이번 비교에서 추가하지 않는다.

### 경로 전환 프롬프트와의 분리

[#36의 최신 설계][route-study]는 경로 메뉴를 주고 연속 3회 평가값이 개선되지 않으면 다음 경로로 이동하도록 지시한다.
[#38의 패턴 조건][pattern-study]도 패턴 순서와 같은 정체 기반 전환을 지시한다.
이들은 프롬프트에서 모델에 전환을 요청하는 조건이다. 이번 정책은 검증 결과를 읽고 다음 요청의 행동과 기준 후보를 하네스가 지정한다.

| 구분 | #36 / #38 | 이번 첫 비교 |
| --- | --- | --- |
| 전환 근거 | 원본의 구조·패턴, 평가값 정체 | proof_error와 incomplete의 구분 |
| 제어 위치 | 프롬프트 지시 | 모델 요청 전 정책 결정 |
| 전환 대상 | 제시한 경로 또는 패턴 | 현재 실패 후보 수리 또는 best에서 재탐색 |
| 첫 비교 사용 | 제외 | 두 수리 정책만 비교 |

같은 경로 전환 프롬프트를 두 조건에 주더라도 그 전환이 수리 정책의 효과를 가릴 수 있다.
따라서 `type-hard-route`, `pattern`, `route_cue`, 3회 정체 전환, 여러 프롬프트 중 최선 선택은 첫 비교에서 사용하지 않는다.
그 조합은 수리 정책 효과를 확인한 뒤 별도 실험으로 다룬다. 여러 실행 중 최선 선택의 비용도 별도로 합산해야 한다.

공통 프롬프트는 main의 [v4 파일](../prompt-design/p01-p05-reasoning-prompts.v4.en.json)을 출발점으로 PR B에서 `repair-policy-common-v1`을 만든다.
출발 파일의 SHA-256은 `e1fbd28df503d894f3cf90e30818dea9ccb046553243b5ac21b8510c69c9d27c`이다.
v4에도 독립적인 행동 지시가 있으므로 원문을 그대로 쓰지 않는다. 두 조건에 같은 다음 편집을 적용한다.

| v4 요소 | 공통 편집 계획 |
| --- | --- |
| 목적값·토큰 정의·HB 손익·검증 규칙·개별 수정 방법 | 유지한다. 각 방법은 정책이 지정한 기준 후보에 적용한다. |
| `case_prompts` | 모든 문제에서 비운다. 기존 문제별 수동 힌트를 가져오지 않는다. |
| `The original proof is already a valid starting point.`로 시작하는 문단 | 제거한다. 첫 3개 후보에서 두 경로를 의무적으로 시험하는 규칙을 없앤다. |
| `Distinguish a missing mathematical premise`로 시작하는 문단 | 오류 수리 시 타입·가정·인자·등식 방향을 확인하는 일반 지침으로 대체한다. 실패 횟수에 따른 별도 제어는 넣지 않는다. |
| `When few attempts remain`으로 시작하는 문단 | best 보존과 출력 계약 안내로 대체한다. 잔여 횟수에 따른 별도 경로 선택은 넣지 않는다. |

안전한 수락·예산·종료 조건을 먼저 적용하고, 그다음 해당 요청의 `action`과 `base_candidate_sha256`을 따른다고 두 조건에 명시한다.
일반 수정 지침은 이 행동을 대체하거나 다른 후보로 복귀시키지 않는다. 모델의 실제 준수 여부는 후보 차이와 함께 관찰한다.
PR B에서 편집 전후 diff, 공통 프롬프트, 행동별 지시문, 최종 요청의 해시를 고정한다. 이 문서는 아직 생성하지 않은 프롬프트의 해시를 주장하지 않는다.
입력 묶음의 문제별 힌트와 runner가 덧붙이는 지시도 확인한다. `case_prompts`만 비우고 다른 위치의 힌트를 남기지 않는다.
공통 프롬프트 변경은 두 조건에 동일하게 적용하며, 이 비교를 기존 v4와의 성능 비교로 해석하지 않는다.

## 5. 실행과 기록 계약

PR B의 첫 구현은 이 폴더의 정책·정규화 모듈과 하나의 실험 adapter에 둔다.
공통 evaluator와 모델·비용 adapter는 재사용한다. 별도 비용 계산기나 평가기를 만들지 않는다.
실험 코드 경로와 실행 명령은 PR B에서 확정한다. 이 PR에는 아직 없는 CLI를 실행 예제로 적지 않는다.

결정은 모델 요청 전에 저장한다. 최소 기록은 다음과 같다.

| 구분 | 필드 |
| --- | --- |
| 식별 | run/problem/attempt ID, policy ID·revision, classifier revision |
| 프롬프트 | 원본 v4 파일 해시, 공통 편집 diff·해시, 행동 지시 해시, 문제별 힌트 비활성화 및 요청 조립 설정 |
| 관측 | 원래 verification 결과, policy_state, 오류 위치·원문 근거 해시, goals/local_context의 수집 여부 |
| 이력 | repair_chain_id, repair_calls_used, latest/best/proposed-base 해시, 이미 제출한 후보 해시 |
| 결정 | action, base_candidate_sha256, reason, repair_chain_stop_reason |
| 비용 | 다음 호출의 예약액, 호출별 사용량·비용·cost_basis, 누적 비용, 미확정 상태 |
| 결과 | 요청·응답 해시, 후보 해시, 검증 완료 시각, T/H 표본, best 갱신, selected_origin |

후보의 `policy_state`, 실행 단계, `repair_chain_stop_reason`, 전체 `stop_reason`을 별도 필드로 둔다.
정책 결정 재생은 저장된 사실과 정책 버전으로 같은 행동이 나오는지 확인한다.
다른 정책을 과거 로그에 적용하는 shadow 분석은 분기 확인에만 사용한다. 새 모델 응답의 성능을 추정하지 않는다.

### 후보 수락과 최종 검증

모든 조건에 현재 evaluator의 명제 보존·허용 범위·컴파일·공리 검사와 같은 토큰 계산을 적용한다.
heartbeat는 같은 고정 환경에서 새 Lean 프로세스로 3회 측정한 raw 값의 중앙값을 사용한다.
선택식은 `Q = T/T0 + H/H0`이며 낮을수록 좋다. 동점은 현재 best를 유지한다.
실패한 후보는 선택하지 않는다. 유효한 원본 fallback을 항상 보존한다.

종료 뒤 선택 proof bytes를 고정하고 같은 환경의 새 Lean 프로세스로 재검증한다.
이 단계에서 새 모델 수리를 요청하지 않는다. 판정 불일치는 별도로 보고한다.
선택 후보가 구체적인 proof/정책 오류로 실패하면 원본을 새로 검증해 반환한다. 이 경우 개선량은 0이고 `selected_origin=baseline`이다.
원본도 통과하지 못하거나 timeout·환경·계측 때문에 확정할 수 없으면 최종 결과를 미확정으로 남긴다.
미확정 결과를 성공이나 점수 0으로 바꾸지 않는다. 조건별 건수와 비교 가능한 분모를 표시한다.
원본·후보의 전체 파일 문맥 조립과 최종 검증은 PR B의 실제 Lean 검사에서 확인할 대상이다.

다른 지정 버전의 검증은 선택을 고정한 뒤 수행한다. 그 결과로 모델을 다시 수정하거나 주 선택을 바꾸지 않는다.
호환성은 해당 문제의 실제 지정 버전 수를 분모로 보고한다. 준비되지 않은 환경은 미측정으로 표시한다.

## 6. 데이터와 실행 규모

과거 Week 4 실험과 현재 입력 준비에 웜업 문제가 사용됐다. 웜업 일부를 새로 나눠도 깨끗한 미관측 평가 집합은 아니다.
#36은 P01·P02·P03의 관찰을 경로 설계에 사용했고, #38은 웜업 최종 증명에서 패턴을 추출했다.
이 자료를 검토했다는 노출도 기록한다. 아래 고정 후 확인은 **이번 수리 정책을 추가 조정하지 않는 확인**이며 팀 전체의 미관측 문제라는 뜻이 아니다.
공식 평가에 포함되는지와 연구상 미관측인지도 별개다. 새 평가 목록은 당시 공식 snapshot과 실제 노출 이력을 확인한 뒤 문제 ID로 고정한다.

| 단계 | 제안 범위 | 역할 |
| --- | --- | --- |
| PR B 무과금 확인 | 작은 Lean fixture와 고정 모델 응답 | proof_error/incomplete/복합 오류/정보 누락/예산 중단/최종 실패를 확인 |
| 동작 파일럿 — 보류 | 준비된 P01·P04, 두 조건 각 1회 | 서로 다른 문맥에서 입력·기록·전환을 확인. 효과 추정에는 사용하지 않음 |
| 개발 비교 — 보류 | P01·P03·P04, 두 조건 각 3회 | 오류별 비용과 개선량을 관찰. 변경한 정책은 새 버전으로 구분 |
| 고정 후 확인 — 보류 | P02·P05, 두 조건 각 3회 | 추가 정책 조정을 하지 않는 개발 외 확인. 과거 노출을 명시 |
| 미관측 평가 | 새로운 문제와 별도 고정 목록 | 처음 보는 문제로 일반화를 확인. 문제와 환경이 확보된 뒤 사전 등록 |

파일럿 결과를 본 뒤 유리한 문제만 선택하지 않는다. 환경 준비 실패는 목록에 남긴다.
목록 변경은 정책 효과를 보기 전에 사유와 새 protocol revision을 기록한다.
두 조건에서 incomplete가 발생하지 않으면 정책 노출이 없었던 것이다. 동작 차이를 시험하지 못했다고 보고한다.

반복은 새 모델 이력과 새 실행 폴더로 시작한다. 서로 다른 조건의 후보와 사후 해석을 입력으로 전달하지 않는다.
문제·반복 쌍마다 조건 순서를 교대한다. 실행 순서와 시간은 기록한다. 같은 seed가 같은 후보를 보장한다고 가정하지 않는다.
단일 호스트에서 직렬 실행해 동시 부하를 줄인다. wall time과 heartbeat는 별도로 기록한다.

### 무과금 우선과 보류한 유료 실행안

PR B에서는 고정 응답과 작은 실제 Lean 사례로 상태 분류·행동 전환·best 보존·기록 재생을 검사한다.
예산 중단은 모의 사용량과 비용으로 검사한다. 이 숫자는 실제 API 지출이 아니다.
이 단계는 모델의 행동 지시 준수나 정책의 성능 우월성을 입증하지 않는다.

보류한 초기 확장안은 독립 실행당 **USD 1.50의 비용 기준 한도**다. 실제 실행 규모와 총예산은 무과금 검증 후 다시 정한다.
위 파일럿은 4실행, 개발 비교는 18실행, 고정 후 확인은 12실행이다.
이 확장안의 상한은 각각 USD 6 / 27 / 18, 합계 USD 51이다. 현재 진행 범위에 포함하지 않는다.
새로운 평가 집합과 보조 복구 실험도 이 금액에 포함하지 않는다.
한 조건만 재실행해 좋은 결과를 고르지 않는다. 추가 실행은 비용과 이유를 모두 기록한다.

첫 backend 후보는 현재 실행기가 지원하는 `openai` / gpt-6.1-sol / high다. 이는 실험 설정 제안이며 현재 가격이나 대회 참가 요건의 주장과 다르다.
현재 직접 API adapter의 `cost_usd`는 usage 기반 추정액이다. 공급자 청구액이라고 표시하지 않는다.
provider 보고액을 사용하는 backend로 바꾼다면 두 조건 모두 바꾸고 별도 protocol로 실행한다.
이전 구독 token과 새 API 비용은 같은 비용 축으로 합치지 않는다.

호출 전 예약, 최대 출력, 호출 수 안전 한도, 문맥 한도, Lean timeout, 가격 snapshot은 두 조건에서 같게 고정한다.
원래 실행기의 미정산·상한 위반 중단을 유지한다. 과금 불명 호출을 무료로 처리하거나 자동 재시도하지 않는다.
같은 한도는 같은 실제 지출을 뜻하지 않는다. 남은 예산으로 안전한 호출을 예약할 수 없으면 그 사유로 종료한다.

실행 전 protocol에는 정확한 모델/adapter/정책/평가기 커밋, 입력·프롬프트·가격 해시, 환경 pin, 모든 수치 한도, 순서, 총 예산을 채운다.
sampling/seed 등 공급자가 제공하지 않는 설정은 null과 사유를 기록한다. 현재 시점의 요금·모델 설정은 실행 준비 때 확인한다.

## 7. 지표와 해석

### 주 실험: 정상 증명의 개선

주 지표는 실행 한도 안에서 최종 재검증한 후보의 `Q`다. 원본의 Q는 2다.
실행 중 선택한 값과 최종 재계측한 값은 둘 다 저장한다. 재계측값으로 과거 선택을 다시 쓰지 않는다.

- 같은 문제의 조건별 3회 평균 Q와 범위를 보고한다. 문제별 평균에 같은 가중치를 준다.
- 대응 차이 `Q(state-aware) - Q(uniform)`를 문제별로 보고한다. 음수는 상태별 정책의 개선이다.
- proof token/HB 감소율, 생성 후보 선택률, 원본 유지율, 최종 미확정 건수를 함께 표시한다.
- 성공한 수리의 비용만 평균내지 않는다. 전체 호출의 비용·실패·중단 사유를 포함한다.
- incomplete 노출, repair/replan 횟수, 수리 묶음 길이, 중복 후보, 전환 후 유효 후보와 개선 후보를 별도로 센다.

누적 비용 USD 0.50 / 1.00 / 1.50에서 이용 가능한 best의 Q를 보고한다.
누적 비용은 후보를 만든 호출까지의 비용이다. 후보는 Lean 검증이 끝난 뒤에만 이용 가능하다.
체크포인트를 넘긴 호출의 개선은 그 이전 지점에 넣지 않는다. 조기 종료는 마지막 확인된 best를 유지한다.
비용 미확정으로 지점 판정이 불가능하면 null로 표시한다. 결과 누락 수와 알려진 부분합을 함께 표시한다.
최종값 차이가 작으면 같은 proof의 추가 재계측을 두 조건에 같은 규칙으로 적용하고 변동을 보고한다.

### 보조 실험: 동일 실패에서의 행동

주 루프에서는 정책마다 발생하는 오류가 달라진다. 오류별 복구율의 분모도 달라질 수 있다.
같은 실패에서의 효과를 보려면 고정한 실패 후보·문맥·진단으로 별도 비교한다.
기존 로그의 실패 또는 통제된 변형을 사용할 수 있지만, 출처와 선정 규칙은 실행 전에 고정한다.
두 조건에 같은 실패 후보, 진단, 원본 문맥, 당시의 검증된 best를 제공한다. 이로써 `replan_from_best`도 같은 의미로 실행할 수 있다.
best나 원본을 그대로 반환한 경우는 복구 성과로 세지 않고 복귀로 표시한다. 첫 유효한 새 후보까지의 비용과 best 대비 개선 여부를 따로 측정한다.
원본을 숨기고 검증된 best도 주지 않는 과거 V-B 과제에는 이 정책을 그대로 적용할 수 없다. 그 과제는 이번 범위에서 제외한다.
이 보조 실험은 별도 예산·protocol을 사용한다. 주 리팩터링 결과와 합산하지 않는다.

## 8. PR B와 C의 통과 기준

### PR B: 정책을 실행하기 전에

- 동일 상태 snapshot에서 두 조건의 차이가 incomplete 행동 행에만 생기는지 확인한다.
- proof_error와 incomplete의 공존, native goal 미수집, timeout, 금지 공리를 혼동하지 않는지 확인한다.
- 수리 0/1/2회 경계, 중복 후보, 응답 거절, 예산 소진에서 올바른 base와 종료 이유를 기록한다.
- 실패 후 best 보존, 최종 재검증 실패, 원본 fallback, 미확정 결과를 확인한다.
- 저장된 요청의 실제 base와 decision 해시가 일치하는지 확인한다. 기록 재생에는 모델·Lean 호출을 하지 않는다.
- 각 상태의 작은 실제 Lean 사례를 확인한다. 모의 compiler 검사와 실제 검증을 구분해 보고한다.
- 두 조건 모두 같은 진단 사실·점수·프로파일 설정을 받는지 확인한다.
- 첫 요청이 조건 간 같은 바이트인지 확인한다. 같은 상태 snapshot에서는 허용한 행동·기준 후보·행동 지시 외의 차이를 거부한다.
- v4의 공통 편집 diff와 모든 입력 경로를 검사해 문제별 힌트, 경로 메뉴, 별도 정체 전환이 남지 않았는지 확인한다.
- PR 상태표 이후의 변경을 확인하고 실행 코드·프롬프트·입력·환경 기준을 두 조건에서 함께 고정한다.
- 입력·코드·정책·가격 snapshot과 실행 명령을 보관한 뒤 유료 실행 준비를 완료한다.

### PR C: 결과를 해석한 뒤

설계한 전체 실행의 결과와 누락·실패를 보고한다. 문제 하나의 최고 결과만으로 기본값을 바꾸지 않는다.
개발 외 확인에서 개선 방향과 비용을 대조하고, 오류별 손해와 정책 전환 노출을 함께 검토한다.
작은 표본으로 차이를 확정하기 어렵다면 결론을 보류한다. 정책을 선택 기능으로 유지할 수 있다.
정규화·결정 기록처럼 재사용 가능한 기능과 정책 기본값 채택은 별도로 판단한다.
점수 피드백의 단계별 제공, 반복 오류 기반 조기 전환, 최종 실패 후 모델 재수리는 후속 실험으로 남긴다.
