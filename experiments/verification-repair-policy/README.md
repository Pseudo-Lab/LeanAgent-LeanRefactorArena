## 1. 연구 질문과 PR 범위

> #37의 Controller·Planner·Worker를 공통 기반으로 사용할 때, Auto Solver → Recursive Repair를 추가하면 같은 전체 예산에서 실패 후보를 더 많이 복구하고 최종 proof의 token·heartbeat 목적값도 개선하는가?

Auto Solver가 남긴 목표를 지역 문맥과 함께 하위 문제로 구성한다.
LLM이 생성한 하위 증명에 남은 목표가 있으면 같은 검증·자동 전술·수리 절차를 다시 적용한다.
**Recursive Repair는 필수 범위**다. 같은 전체 proof를 반복 요청하는 retry와 구분한다.
`proof_error/incomplete`는 관측값으로 남길 수 있으나 그 라벨 하나로 수리·재탐색 행동을 결정하지 않는다.

## 2. 근거와 해석 한계

### APOLLO의 흐름

[APOLLO v2 §3.2–3.5][apollo]는 실패 블록을 정리하고 미해결 부분을 표시한다.
Auto Solver가 각 목표에 `hint`와 자동 전술을 적용한다.
남은 목표는 지역 가정·정의·앞서 증명한 보조정리를 포함한 문맥과 함께 새 보조정리로 추출한다.
LLM이 생성한 하위 증명에도 검증·정리·Auto Solver를 적용하고, 깊이 한도 안에서 반복한다.
수리한 블록을 조립한 뒤 전체 증명에서 `sorry`·`admit`이 제거됐는지 확인한다.

이 실험은 해당 흐름을 현재 리팩터링 환경에 적용한다. APOLLO 전체의 재현 실험은 아니다.
논문의 전체 시스템 성능을 Auto Solver 단독 효과나 이 저장소의 목적값 개선 근거로 사용하지 않는다.
초기 증명 전략이 잘못되면 국소 수리로 해결하기 어렵다. 복구된 증명이 더 길거나 느릴 수도 있다.

### Week 4 리포트에서 가져올 계약

[Week 4 리포트][report]의 native InfoTree 기반 목표·지역 문맥 수집과 전체 파일 재검증을 참고한다.
리포트의 V-A 고정 사례 90개에서는 단순 판정이 38건을 오수락했고 엄격 판정은 0건이었다.
이 결과는 최종 명제·공리 검사를 유지할 근거이며 일반적인 오수락률은 아니다.
V-B의 `proof_error` 복구는 B1 42/45, B2 44/45이고 `incomplete` 복구는 20/45, 17/45였다.
진단 표현·지침·이력·비용이 함께 달랐으므로 이 차이로 재귀 수리나 재탐색의 우열을 판단하지 않는다.

리포트의 손상 proof 복구율과 정상 원본에서 시작하는 리팩터링 성과를 합산하지 않는다.
당시 구독 CLI의 token 사용량은 현재 API 달러 비용과 같은 축이 아니다.
과거 리포트의 정상 정답·최선 후보를 새 생성 모델의 입력으로 제공하지 않는다.

## 4. Auto Solver → Recursive Repair 흐름

1. Worker의 루트 후보를 검증한다. 유효하면 공통 평가·선택 절차로 보낸다.
2. 실패 후보에서 지원하는 proof 블록과 native 목표·지역 문맥을 추출한다.
3. 각 목표에 Auto Solver를 적용한다. 해결된 블록은 증거와 함께 보관한다.
4. 남은 목표를 하위 문제로 구성한다. Recursive Repair 조건에서만 Worker에 그 목표의 증명을 요청한다.
5. 생성된 하위 증명을 검증한다. 내부에 남은 목표가 있으면 2–4단계를 해당 하위 증명에 다시 적용한다.
6. 해결한 결과를 부모에 조립하고 검증한다. 모든 부모를 따라 루트까지 반환한다.
7. 루트가 완성되면 원래 문맥의 전체 파일을 새 Lean 프로세스로 검사하고 목적값을 측정한다.
8. 수리 한도·반복·추출 불가·운영 실패에서는 근거와 잔여 목표를 Controller에 반환한다.

예를 들어 `g₁`은 자동 전술로 해결하고 `g₂`에는 Worker를 사용한다.
`g₂`의 하위 증명에 `g₂₁`이 남으면 그 목표에도 Auto Solver → Recursive Repair를 적용한다.
성공한 결과를 `g₂`, 루트 순서로 조립한다. 부분 성공은 루트의 검증 통과와 다르다.

### v1에서 지원할 변환

Lean이 구문을 읽을 수 있고 source 위치와 native 목표를 대응시킬 수 있는 tactic `by` 블록을 대상으로 한다.
전체 proof body와 명시적인 중첩 `have ... := by ...`를 지원 범위로 둔다.
실패 tactic을 포함한 나머지 부분 또는 실패한 중첩 proof body를 source 범위에 따라 분리하고, 분리 전후 코드를 보존한다.
실패 tactic 없이 목표만 남은 경우에는 블록 끝의 native 상태와 삽입 위치를 사용한다.
자동 구문 추측·임의 문자열 치환·정리 명제나 외부 선언 변경은 하지 않는다.
기존 바인더·지역 가정·instance·필요한 환경을 보존할 수 없으면 `extraction_unavailable`로 반환한다.
`induction ... with`의 누락된 경우도 실제 목표와 삽입 위치를 확보한 경우에만 지원한다.
그렇지 않으면 미지원 사례로 분모에 남긴다. 모든 경우 누락을 수리한다고 가정하지 않는다.

중간 분리에 임시 `sorry`를 사용할 수 있지만 그 자료는 최종 후보·점수에 포함하지 않는다.
하위 목표는 원래 위치의 문맥에서 검사하고 의존 관계 순서로 조립한다.
아직 증명하지 않은 다른 hole을 검증된 보조정리로 취급하지 않는다.
부모 문맥이 바뀌면 의존하는 하위 증명도 재검증한다. 독립성이 확인되지 않은 목표를 병렬로 풀지 않는다.

## 5. 연결·기록 계약

### 제안하는 입력과 반환값

| 계약 | 필수 내용 |
| --- | --- |
| `RepairRequest` | run/problem/attempt·route ID, 루트 후보와 검증된 best의 해시, 원래 파일·명제·환경, 전체 진단, 실행 예산 핸들, protocol revision |
| `RepairNode` | node/parent ID, 깊이, source 범위, 목표·지역 문맥과 수집 근거, 문맥 의존 관계, proof·전술 시도·요청 기록 |
| `SubproofRequest` | 부모·노드 ID, 증명할 목표와 해당 지역 문맥, 고정 환경·출력 계약, 남은 호출·출력 한도. 전체 proof 최적화를 새로 요청하지 않음 |
| `RepairResult` | 결과 상태, 완성 후보 또는 잔여 목표, 부모·자식 관계, 검증 근거, 실제/모의 비용·자원, 반환 사유 |

결과 상태는 `verified`, `residual`, `extraction_unavailable`, `unsupported`, `limit`, `cycle`, `operational_error`로 분리한다.
`verified`는 루트 전체 검증·정책·공리 검사를 통과했을 때만 반환한다. 목적값 개선 여부는 Controller가 별도로 판단한다.
하위 노드의 `solved`와 최종 `verified`, 노드 반환 사유와 전체 실행의 `stop_reason`을 구분한다.
현재 진단의 `proof_error/incomplete` 같은 분석 라벨은 원래 근거와 함께 보존한다.

### 목표·중복·진행 여부

목표는 native 수집 결과를 사용한다. `goals=null`은 미수집이고 `goals=[]`와 다르다.
`error:`와 `error(code):`를 모두 처리하고 원문·오류 코드·source 위치를 남긴다.
목표 수 감소만으로 수학적 진전이나 경로 개선을 판단하지 않는다.

후보 중복은 Controller의 고정 정규화 규칙을 공유한다. 미완성 결과를 성공 캐시로 사용하지 않는다.
v1의 재귀 순환 키는 환경 pin과 고정 출력 옵션으로 직렬화한 목표·순서 있는 지역 문맥의 해시다.
줄바꿈만 정규화하며 식별자·가정·들여쓰기·암묵적 문맥을 임의로 제거하지 않는다.
현재 조상 경로에 같은 키가 나타나면 순환으로 반환한다. 의미적 동치까지 검출한다고 주장하지 않는다.
이 비교는 깊이 1 이상의 미해결 목표 노드끼리 수행한다. 루트 후보 컨테이너와 첫 추출 목표가 같다는 이유로 최초 수리를 차단하지 않는다.
직렬화에 필요한 문맥이 없으면 해시를 추측하지 않고 추출 실패로 처리한다.

### 예산과 재현 기록

노드 생성·모델 요청 전에 결정과 부모 관계를 저장한다. 모든 노드는 루트 실행의 같은 비용 원장을 사용한다.
Planner·루트 Worker·repair Worker 비용을 모두 포함한다. 자식마다 예산을 초기화하지 않는다.
호출 전 예약, 미정산·과금 불명 보존, 상한 위반 중단 규칙을 재사용한다. 미수신 비용을 0으로 처리하지 않는다.
Auto Solver는 API 호출 없이 실행하지만 Lean 시간·메모리와 실행 횟수는 기록한다.

protocol, 코드·환경·입력·프롬프트 해시, 노드 이벤트, 전술별 입력/결과, 요청/응답, 비용 영수증,
source 변환 diff, 원시 진단, 재조립 결과, 선택·최종 검증 결과를 보관한다.
기록 재생은 저장된 관측으로 결정·노드 관계·한도·선택을 재계산한다. replay 자체에서 모델·Lean을 호출하지 않는다.
실제 Lean 재실행 검증은 replay와 별도 명령·결과로 구분한다.

| `recursive-repair-v1` | 자동 수리 조건 + 잔여 목표의 재귀 Worker 호출 | 자동 수리 대비 Recursive Repair의 추가 효과 |

기준과 재귀 수리 비교는 전체 추가 하네스의 효과다.
자동 수리와 재귀 수리 비교는 재귀 단계의 추가 효과이며 두 조건의 추출기·전술·조립기는 같다.
논문의 Auto Solver 단독 기여를 분리한 비교라고 표현하지 않는다.
세 조건을 모두 즉시 유료 실행하는 계획은 아니다.

모델, 고정 원본·초기 best, 환경, 평가기, Controller·Planner 설정, 루트 프롬프트, 진단 사실과 길이 제한을 고정한다.
동일한 입력 snapshot에서 조립한 Planner·루트 Worker 요청은 조건 간 같아야 한다.
독립 실행에서 Planner 응답이 달라지면 이후 Worker 입력까지 같다고 가정하지 않는다.
하위 문제용 프롬프트만 별도 계약을 사용하고 그 입력·호출·비용도 기록한다.
처리 결과에 따라 이후 후보·이력·Planner 호출 시점이 달라지는 것은 실험 결과다. 이를 강제로 같게 만들지 않는다.

공통 입력에는 실행 환경의 전술 가용성 같은 사실을 유지한다.
문제별 수동 전략·정답 힌트는 최상위 필드뿐 아니라 `context`와 runner가 붙이는 문장까지 검토한다.
v4 프롬프트나 #36/#38의 독립적인 경로 전환 지시를 그대로 중첩하지 않는다.
#37 Controller·Planner의 경로 제어와 충돌하는 문장을 공통 편집하고 diff·최종 요청 해시를 PR B에 보존한다.
현재 공개되지 않은 #37 프롬프트나 API의 정확한 형태를 이 문서에서 확정된 것으로 취급하지 않는다.
새 점수 노출 방식, 외부 lemma 검색, 별도 local golf는 이번 비교에 추가하지 않는다. HB profile은 세 조건 모두 끈다.

## 7. 무과금 v1의 고정 한도

아래는 작은 fixture의 동작 검증을 위한 설계값이다. 논문이나 과거 성능에서 얻은 최적값이 아니다.
변경이 필요하면 protocol revision과 사유를 남기고 관련 조건을 함께 다시 검증한다.

| 항목 | `offline-v1` 값과 의미 |
| --- | --- |
| 실제 API 비용·호출 | USD 0 / 0회. 네트워크 모델 호출은 차단하고 고정 응답만 사용 |
| 재귀 깊이 | 루트 0, 자식 1, 손자 2까지. 깊이 2에서도 직접 완성은 가능하지만 자식 추가는 불가 |
| 하위 노드 수 | 루트 수리 1건당 총 8개. 생성에 실패한 예약 노드도 포함 |
| repair Worker 요청 | 노드당 최대 2회, 루트 수리당 합계 6회. 거절·실패 응답도 포함 |
| 전체 모델 dispatch | fixture 실행당 Planner·루트 Worker·repair 합계 32회. 모의 비용 한도 검사는 별도 fixture 값 사용 |
| Auto Solver | 목표 상태당 아래 전술 최대 6개, 같은 상태·전술 쌍은 한 번만 시도 |
| Lean 자원 | 수리용 subprocess 최대 64회/루트, 각 10초·메모리 2,048 MiB. 하위 노드가 한도를 공유 |
| 수리·전체 실행 시간 | 루트 수리당 120초, fixture 실행당 600초. 최종 검증도 전체 시간에 포함 |

전술 후보 순서는 `rfl`, `assumption`, `trivial`, `simp`, `omega`, `grind`다.
각 환경에서 실제 가용성을 사전 확인하고 사용할 목록과 해시를 고정한다.
해당 상태를 완전히 닫지 못한 전술 시도는 rollback한다. v1은 전술 조합의 무제한 탐색을 하지 않는다.
`hint`, `nlinarith`, `ring` 등을 논문에 있다는 이유만으로 추가하지 않는다. 전술 목록 확장은 새 protocol이다.

루트 후보는 깊이 0의 컨테이너다. 처음 추출한 목표는 자동 전술의 성공 여부와 관계없이 깊이 1의 노드로 기록한다.
그 노드의 Worker 증명에서 새 목표가 나오면 깊이 2가 된다. 같은 노드의 재시도는 깊이를 늘리지 않고 호출 한도를 사용한다.
자원 한도를 먼저 확인하고 dispatch 전에 예약한다. 한도에 걸리면 부분 결과와 이유를 보존한다.
수리용 Lean 호출 한도와 공통 초기 평가·최종 검증 호출을 구분해 기록하되 모두 전체 시간·자원 집계에 포함한다.
마지막 허용 호출에서 완성된 후보도 검증·선택한다. 종료 시 최종 검증할 시간이 없으면 결과를 미확정으로 남긴다.
실제 API 비교의 가격·출력 토큰·호출 예약·총비용 상한은 무과금 확인 뒤 별도 protocol에서 고정한다.

fixture의 정답 응답은 테스트 전용이다. 실제 성능 평가의 모델 입력으로 전용하지 않는다.

이 결과는 구조·계약 검증이며 실제 LLM의 하위 목표 해결률이나 API 절감률이 아니다.

### PR C의 고정 실패 후보 평가

실제 실패 corpus는 공개 원시 후보·원래 문맥·지정 환경을 확보한 뒤 별도 manifest로 동결한다.
우선 대상은 기존 P01–P05 입력과 대응하는 공개 생성 이력이다.
선택한 source run의 모든 실패 후보를 포함하고 출처·attempt ID·해시·중복 여부를 남긴다.
환경 미준비·추출 불가도 전체 분모에서 제거하지 않는다. unique 후보 분석은 별도로 제시한다.
정상 원본은 현재 리팩터링 과제의 공통 출발점으로 사용할 수 있으나, 팀의 이전 최선·제출 proof는 입력하지 않는다.
fixture와 실제 생성 실패 corpus를 합산하지 않는다. 새 corpus의 결과를 본 뒤 전술·선정 규칙을 바꾸지 않는다.

#37의 7회 실행·99개 실패는 현재 공개된 집계이며 원시 후보를 확보했다는 뜻이 아니다.
따라서 PR A는 실제 corpus의 개수·해시나 새로운 복구 성능을 주장하지 않는다.
확보하지 못하면 fixture 검증만 보고하고 실제 실패 corpus 평가는 미측정으로 남긴다.
무과금 corpus 평가에서는 Auto Solver의 실제 복구·목적값을 측정할 수 있다.
fixture로 대신한 Recursive Repair 결과를 실제 생성 후보에 대한 성능으로 계산하지 않는다.

## 9. 평가 지표·선택·최종 검증

### 수리 단계의 지표

- 전체 실패 후보 중 native 목표·문맥 추출 가능 비율. 운영 실패·미지원·미수집 건수도 함께 보고한다.
- Auto Solver만으로 루트 전체가 검증된 비율. 목표 단위 해결률과 구분한다.
- Auto Solver 후 남은 후보 중 Recursive Repair로 검증된 비율과 전체 실패 후보 기준 복구율을 함께 보고한다.
- 복구 후보 중 당시 best보다 목적값이 개선된 비율. 원본/best를 그대로 반환한 것은 복귀로 표시하고 복구 성과로 세지 않는다.
- 재조립·최종 검증 실패, 최대 도달 깊이, 노드·호출·전술 횟수, 종료 사유, 전체 API 비용·Lean 시간·메모리 한도.

고정 실패 corpus에서는 모든 조건에 같은 실패·문맥·진단·당시 best를 제공한다.
기준 조건의 단순 거절과 수리 조건을 비교한 오프라인 결과를 생성 루프 전체의 효과로 해석하지 않는다.
생성 루프에서는 조건별로 실패 분포가 달라지므로 조건부 복구율만으로 정책 우열을 판단하지 않는다.

### 최종 품질과 공통 수락

선택식은 `Q = T/T0 + H/H0`이고 낮을수록 좋다. 원본의 Q는 2다.
T는 같은 `lean-source-anchored-v1` token 계산, H는 같은 환경의 새 Lean 프로세스 3회 측정 중앙값이다.
공통 원본 측정 T0/H0를 문제별로 동결한다. 원본 검증 실패나 0·미확정 분모에서는 비교를 시작하지 않는다.
동점은 현재 best를 유지한다. 최종 전체 명제·허용 범위·공리 검사를 통과한 후보만 선택한다.
중간 sketch의 컴파일 성공, `goals=[]`, 하위 노드 해결만으로 루트를 수락하지 않는다.

실행 종료 후 선택 proof bytes를 고정하고 새 Lean 프로세스로 재검증한다. 이 단계에서 모델 수리를 다시 요청하지 않는다.
구체적인 proof/정책 실패이면 원본을 다시 검증해 반환한다. 원본 복귀의 개선량은 0이다.
환경·timeout·계측 오류 또는 원본도 확인 불가이면 미확정(null)이다. 이를 성공이나 Q=0으로 바꾸지 않는다.
선택 시 측정과 최종 재계측을 모두 저장하고 최종값으로 과거 선택 이력을 다시 쓰지 않는다.

### 후속 생성 루프 비교

실제 #37 통합과 무과금 검사를 통과한 뒤 실행 문제·독립 반복 수·모델·가격 snapshot·예산을 별도 등록한다.
세 조건의 전체 API 비용 상한과 전체 시간 상한을 같게 두고 실제 소비 차이를 함께 보고한다.
문제·반복별 조건 순서를 교대하고 새 이력·실행 폴더로 시작한다. 같은 seed가 같은 응답을 보장한다고 가정하지 않는다.
동일 실패의 수리 비교와 정상 원본에서 시작한 루프 비교를 별도 표로 보고한다.
주 비교는 `Q(recursive) - Q(auto)`와 `Q(recursive) - Q(baseline)`이며 음수가 개선이다.
문제별 대응 차이와 반복 변동, 원본 유지·최종 미확정 건수, 같은 비용 지점에서 이용 가능한 best를 보고한다.
비용 지점은 실행 전에 고정한다. 호출 비용과 검증이 완료되기 전의 후보를 과거 지점에 소급하지 않는다.
표본이 작거나 repair가 거의 호출되지 않으면 결론을 제한한다. 수리 호출 노출과 실패 분모를 명시한다.
과거 보고서·웜업을 검토한 노출을 기록하며 같은 문제 재사용을 미관측 일반화 평가로 부르지 않는다.
