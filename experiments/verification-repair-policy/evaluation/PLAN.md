# PR C: 고정 실패 후보의 무과금 평가

이 계획과 `corpus.json`은 새 Auto Solver 결과를 생성하기 전에 고정한다.
PR B `14968c2`의 수리 로직과 공통 평가기를 사용한다. 실제 모델 호출은 0회다.

## 입력 선정

- 1차 출처인 #37의 API v5 실행과 7회 실행·99개 실패 집계는 원시 이력이 미공유다. 확보한 것으로 취급하지 않는다.
- 대체 출처는 사용자가 제공한 Week 4 리포트의 공개 P_A 생성 이력이다. 저장소 `Pseudo-Lab/LeanAgent`, revision `e302e89eadf2c7eb2b65f0035f7dbba0b8e09130`, run `20261024T000653+0900`이다.
- 검증된 수집기 버전인 Lean 4.26.0과 Strata `451e5f047bafa010d178856db76c00029bfa4d7f`를 사용하는 P01–P03을 선정한다. A0–A3 × 반복 1–3의 모든 36개 이력을 포함한다.
- 생성 후보 88개 중 당시 `eligible=false`인 49개를 모두 포함한다. 같은 문제·원래 문맥·줄바꿈 정규화 코드 기준 고유 후보는 44개다.
- V_A/V_B의 인위적 손상 입력과 PR B의 소형 fixture는 이 모집단에 넣지 않는다. 과거 조건별 차이를 이번 수리 조건의 효과로 해석하지 않는다.
- 출처 blob과 SHA-256, 후보 순서, 당시 판정, 중복 연결, 해당 호출 **이전**의 best를 보존한다. 나중에 찾은 최선 후보는 수리 입력에 넣지 않는다. Worker 자체를 호출하지 않는다.

## 실행 조건

조건은 `no-repair`와 `auto-solver-v1`이다. 전자는 동일 실패를 그대로 거절하고 이전 best를 유지하는 정적 기준이다. 독립적인 Planner/Worker 생성 루프가 아니다.
`recursive-repair-v1`의 실제 모델 효과는 미측정이다. PR B의 고정 응답 검사를 성능 표에 합산하지 않는다.

전술은 `rfl`, `assumption`, `trivial`, `simp`, `omega`, `grind` 순서다. 같은 환경에서 파싱 가용성을 확인한다.
B의 한도를 유지한다: 깊이 2, 노드 8, 수리용 Lean 최대 64회, 프로세스당 10초·2,048 MiB, 수리 120초, 사례 600초.
코드의 모델 dispatch는 금지한다. 모의 비용이나 과거 구독 token을 API 달러 비용으로 환산하지 않는다.

Strata의 원본 전체 파일은 target 이후에 target을 참조하는 정리가 있다. target을 지운 preflight 대신 compiler·source·빌드 라이브러리 pin과 **원본 전체 파일 검증**으로 문맥을 확인한다.
가용성 검사는 원본 target을 유지하고 같은 파일 끝에 parser probe를 추가한다. 후보 검증과 최종 수락은 원래 전체 문맥을 사용한다.
환경과 원본 기준 측정은 문제별로 한 번 공유한다. 컴파일된 라이브러리는 기존 `prepared.py`로 시작·종료 시 전체 해시를 검사하고 각 호출 전 변경을 확인한다.

## 실행 전 준비에서 확인한 제한

고정 upstream의 80개 의존 빌드 작업은 완료했다. 원본 검증 준비 검사에서 P01·P02는 프로세스당 10초를 초과했다. P03 원본은 전체 검증과 3회 계측을 통과했다.
이것은 수리 결과를 보기 전의 준비 관측이다. 이번 평가에서는 한도를 늘리지 않는다.
본 실행에서 원본이 확인되지 않으면 그 문제의 모든 사례를 `baseline_unverified`로 남기고 복구·품질은 null로 기록한다. native 수리 실패나 복구율 0으로 바꾸지 않는다.

## 측정과 완료 기준

1. 전체 49개와 고유 44개의 분모를 모두 보존한다. 문제·과거 상태별 준비/재현/추출/복구/미확정 수를 보고한다.
2. 당시 실패가 이번 환경에서 재현되는지 먼저 확인한다. guard 거절과 Lean proof 실패, 운영 실패를 구분한다.
3. 자동 수리는 루트 전체의 명제·공리·계측 검증을 통과해야 복구다. 원본 복귀는 복구가 아니다.
4. `Q=T/T0+H/H0`, 낮을수록 좋다. 공통 원본 T0/H0를 고정한다. H는 새 Lean 프로세스 3회의 raw heartbeat 중앙값이다. 복구와 당시 best 대비 개선을 분리한다.
5. 미수집 목표와 미확정 품질은 null이다. 관측된 복구 수/전체 후보 수와 측정 가능한 사례의 복구율을 별도로 표시한다.
6. 선택한 증명은 새 프로세스로 전체 재검증한다. proof 실패면 원본을 재검증한다. 운영 실패면 미확정이다.
7. 원시 compiler source·로그, native 상태, 결정 tape, 결과와 해시를 보존한다. replay는 compiler나 모델을 호출하지 않고 동일 결과를 재계산해야 한다.
8. 실패·무효과·미측정 결과도 그대로 게시한다. 이 결과로 #37의 경로 고착 해결, API 비용 절감 또는 재귀 수리의 모델 효과를 주장하지 않는다.
