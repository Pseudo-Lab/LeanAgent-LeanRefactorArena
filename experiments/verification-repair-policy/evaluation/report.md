# PR C: 실제 생성 실패 후보의 무과금 평가

**당시 자동 수리 대상 4개는 모두 native 상태를 기록했지만 복구하지 못했다.**
선정한 49개 전체에 대한 수리 성능은 확정할 수 없다. P01·P02의 43개는 원본 검증이 10초 한도를 넘었고,
P03의 2개는 과거 실패가 현재 평가기에서 재현되지 않았다. 실제 Recursive Repair 모델 효과와 #37 생성 루프 효과는 미측정이다.

**후속 정정 (2026-11-01):** 이 4개 중 `P03-A2-r3-c01`, `P03-A2-r3-c02`는
중첩 `have … := by`의 실제 잔여 목표 대신 바깥 `UpdateStates …` 목표를 선택했다.
따라서 위의 native 수집 4건을 모두 올바른 목표 추출로 해석할 수 없다.
실제 수리 대상은 두 사례 모두 `ks'.Disjoint (List.map Prod.fst (ks.zip vs))`다.
원시 syntax 블록 경계로 대상을 제한하고 이 두 기록을 회귀 검사에 추가했다.
또한 후속 P02 정상 원본은 60초 제한에서 전체 검증 3회 모두 통과했다.
당시 10초 결과·rows·archive는 유지한다. 수정된 방법으로 49개를 재실험한 결과가 아니다.
자세한 변경과 새 생성 루프 검증은 [연결 문서](../INTEGRATION.md)를 참조한다.

## 무엇을 실행했는가

[실행 전 계획](PLAN.md)과 [후보 목록](corpus.json)은 commit `6f4b0b4`에서 먼저 고정했다.
미빌드 의존성 디렉터리를 준비 경로에서 제외한 수정 후, 깨끗한 commit `c60b6b6d7ea111d3451e14af52c994cd1cc71f8a`를 보존하여 실행했다.
이 준비 수정은 후보·선정 규칙·전술·자원 한도를 바꾸지 않았다. 본 실행 후 수리 로직이나 전술을 결과에 맞춰 조정하지 않았다.

원래 우선 출처였던 [#37](https://github.com/Pseudo-Lab/LeanAgent-LeanRefactorArena/issues/37)의 API v5 원시 이력은 미공유다.
따라서 그 이슈의 99개 실패를 확보하거나 재평가했다고 주장하지 않는다.
대신 사용자 리포트의 [Week 4 P_A 생성 이력](https://github.com/Pseudo-Lab/LeanAgent/tree/e302e89eadf2c7eb2b65f0035f7dbba0b8e09130/docs/research/verification-repair/%EC%86%90%EC%A7%80%EC%97%B0/experiment%28week4%29/evidence/experiment/runs/20261024T000653%2B0900/runs/P_A)을 사용했다.

- P01–P03, A0–A3 × 3반복의 36개 이력을 모두 조사했다. 생성 후보 88개 중 당시 `eligible=false`인 49개를 선정했다.
- 같은 문제·문맥·코드의 중복 5개가 있어 고유 후보는 44개다. 중복은 목록에서 삭제하지 않았다.
- source config·candidate·terminal JSON 160개의 Git blob 해시와 proof/full-source 해시를 대조했다.
- P04·P05 등 다른 Lean 버전, V_A/V_B 손상 fixture, PR B 소형 fixture는 성능 집합에 포함하지 않았다.
- 입력·환경의 출처는 [source-audit.json](source-audit.json), 호출 직전 best와 개별 source 해시는 [corpus.json](corpus.json)에 있다.

Lean 4.26.0, Strata `451e5f047bafa010d178856db76c00029bfa4d7f`와 고정 plausible revision을 사용했다.
의존성 80개 빌드 작업 후 원본 전체 파일을 검사했다. target 이후의 의존 정리도 유지했다.
컴파일된 라이브러리는 공통 `prepared.py`로 실행 전후 전체 해시와 각 호출 전 변경 여부를 확인했다.

모델 호출은 코드에서 금지했다. 전술은 `rfl`, `assumption`, `trivial`, `simp`, `omega`, `grind` 순서이며
B의 10초/프로세스, 수리 120초, 수리용 Lean 64회, 메모리 2,048 MiB 한도를 유지했다.

모든 잔여 목표를 완전히 열거하거나 다른 모든 국소 수리 방법을 탐색한 결과는 아니다.

## 품질과 자원

복구된 후보가 없으므로 수리로 개선한 best도 0건이다. 복구 후보의 품질 개선율은 분모가 없어 미정의다.
P03의 최종 선택 6개는 모두 전체 재검증을 통과했다. 원본 4개와 당시 best 2개를 유지했다.
유지한 best의 Q 약 0.672와 0.654는 **과거 이력에서 이미 얻은 성과**다. 이번 Auto Solver 개선으로 계산하지 않는다.

선택식은 `Q=T/T0+H/H0`, H는 새 Lean 프로세스 3회의 raw heartbeat 중앙값이다.
원본 유지의 선택 Q는 2다. 새 계측에서 생긴 작은 변동은 [rows.json](rows.json)의 `final_measured_q`에 보존했다.
원본 복귀를 미세한 품질 개선이나 손실로 해석하지 않는다. 원시 결과의 `final_q`는 이 새 계측값이며 파생 표와 구분된다.

| 항목 | 관측 |
| --- | ---: |
| 실제 모델 호출 / API 비용 | 0회 / USD 0 |
| 문제별 공유 준비의 Lean 컴파일 | 7회 |
| 후보별 검증·수리·최종 검증의 Lean 컴파일 | 72회 |
| 위 72회 중 수리용 Lean 컴파일 | 28회 |
| 기록된 공유 단계 시간 합 | 약 43.0초 |
| 기록된 후보별 단계 시간 합 | 약 369.5초 |

Lean 컴파일 79회에는 빌드 80개 작업과 compiler/Git fingerprint 조회를 넣지 않았다.
시간은 해당 로컬 실행의 단계별 경과시간 합이다. 다른 하드웨어의 성능 수치나 API 비용 절감률이 아니다.
`no-repair`는 실패 후보를 수정하지 않고 기존 best를 유지하는 정적 기준이다. 같은 예산의 독립 생성 루프를 실행하지 않았다.

## 기록과 검증

- 보존한 코드·입력·명제·문맥·라이브러리 해시, native source와 로그, 결정 tape, reference 3개와 사례 49개를 [evidence.tar.gz](evidence.tar.gz)에 포함했다.
- subprocess 생성이 금지된 상태에서 reference 3개·사례 49개의 replay와 집계를 재계산했다. 별도 폴더에 압축파일을 풀고 보존 코드로도 replay를 통과했다.
- 새 corpus 계약 테스트와 실제 Lean 소형 adapter 검사를 추가했다. 이 소형 검사는 성능 표에 넣지 않았다.
- 검증 명령·해시·완료 범위는 [validation.json](validation.json), 재현 절차는 [README.md](README.md)에 있다.

## 이번 결과가 요구하는 다음 점검

1. **실제 문맥에 맞는 검증 자원 설계.** fixture용 10초 한도로 P01·P02의 원본조차 확인하지 못했다. 문맥 준비·전체 파일 검증 비용을 계측하고, 한도나 문맥 캐시를 바꿀 경우 새 protocol로 후보 전체를 다시 평가해야 한다.
2. **실제 Worker를 연결한 잔여 목표 수리.** 이번 4개는 현재 자동 전술을 통과하지 못했다. 재귀 Worker를 적용할 입력과 근거는 남았지만, 실제 모델이 해결하는지·비용만큼 이득인지 아직 모른다.
3. **#37 통합 후 생성 루프 비교.** 경로 전환, 반복 실수 감소, 중복 과금 회피는 이번 고정 실패 평가로 검증되지 않았다. 실제 Controller·Planner·Worker revision과 모델·반복·예산을 고정한 비교가 필요하다.

이 결과는 작은 과거 집합의 제한된 평가다. 현재 자동 전술의 유효성이나 Recursive Repair의 우열을 일반화하지 않는다.
