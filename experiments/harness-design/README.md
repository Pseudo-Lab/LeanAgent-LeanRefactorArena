## 2. 참고한 점

1. **처음 보는 문제로 확인**: 하네스를 조정한 문제에서만 점수가 오르고 처음 보는 문제에서는 오르지 않는 경우가 많음(What Evolves When We Talk About Harness Evolution?). 수학 벤치마크 LiveMath에서는 학습용 35문제 중 21문제에 같은 정답 선지가 있어, 하네스가 그 지름길을 배움. 본 벤치마크 50문제는 처음 보는 문제이므로 조정에 쓰지 않은 문제로 따로 확인해야 함.
2. **같은 예산 기준선**: 새 하네스가 나아 보여도 재시도·검증·병렬 샘플로 계산을 더 쓴 효과일 수 있음. 기본 하네스에 같은 예산을 줘서 비교해야 함(같은 글의 budget-matched baseline). 대회는 재시도와 버린 후보까지 문제당 $3에 포함하므로 이 비교가 실제 점수와 같음.
3. **여러 번 시도**: 모델 출력은 실행마다 달라지므로 같은 조건을 여러 번(trial) 돌려야 함(Demystifying evals for AI agents).
4. **회귀 확인과 능력 확인 구분**: 이미 되던 문제가 여전히 되는지(regression)와 새 방식이 더 줄이는지(capability)는 따로 봄(같은 글).
5. **평가기는 루프 밖**: 하네스가 스스로 고칠 수 없는 곳에서 판정함. 현재 하네스는 이미 Lean 검증·공리 검사·선택을 모델 밖에서 하므로 그대로 유지함.

## 3. 문제 분리

웜업 15문제를 조정용 10문제와 held-out 5문제로 나눔. 출처마다 한 문제씩, 출처 안에서 두 번째 번호를 held-out으로 둠.

| 구분 | 문제 |
| --- | --- |
| 조정용 | 1, 3, 4, 6, 7, 9, 10, 12, 13, 15 |
| held-out | 2, 5, 8, 11, 14 |

- 프롬프트, 근방 반경, 예산 배분 같은 설정은 조정용 문제의 결과만 보고 바꿈.
- held-out 문제는 설정을 고정한 뒤 마지막에 한 번만 돌려 보고함.
- 본 벤치마크 공개 후에는 50문제 전체가 처음 보는 문제이므로, held-out 결과가 조정용 결과와 크게 다르면 그 설정은 조정용 문제에만 맞춘 것으로 봄.
- 한계: 블록 전략과 analyze의 유형 기준은 이미 15문제 전체를 보고 정했으므로 held-out이 완전히 깨끗하지는 않음.

## 4. 비교 조건: 근방은 얼마나 붙여야 충분한가

### 아이디어

문제 유형을 분류하고 analyze로 고칠 블록을 고른 이유는 증명 전체가 아니라 필요한 구간만 보려는 것임. 다만 블록 하나만 떼어 보내면 모델이 주변 흐름을 몰라 실패할 수 있음. 그래서 수학에서 한 점이 아니라 그 점의 근방을 보듯, 고칠 블록에 주변 블록을 붙여 보냄.

근방이 얼마나 넓어야 하는지는 통계의 **sufficient statistic** 개념으로 정함. 통계량 T(X)가 sufficient하다는 것은 T(X)만 알아도 데이터 X 전체를 아는 것과 모수 추정에 차이가 없다는 뜻임. 여기서 X는 증명 전체와 문맥, T는 고칠 블록과 그 근방임.

> 고칠 블록의 근방(반경 r)을 T라 할 때, T만 보낸 경우의 성공률과 감소율이 증명 전체를 보낸 경우와 차이가 없으면 T는 이 수정에 대해 sufficient하다고 봄. r = 0, 1, 2, 전체를 같은 예산으로 비교해, 전체와 차이가 없는 가장 작은 r(minimal sufficient 근방)을 찾음. 이 r이 성능을 유지하면서 입력 비용이 가장 작은 설정임.

진짜 sufficiency는 증명할 수 없으므로, 성공률 차이가 없다는 실험 결과로 판단하는 근사임.

### 근방의 정의

근방은 줄 수가 아니라 analyze가 나눈 블록 단위로 정함. 줄로 자르면 `have` 증명 중간이 잘릴 수 있기 때문임. 같은 부모 아래의 형제 블록을 앞뒤로 r개씩 붙임.

반경과 관계없이 항상 같이 보내는 것:

- 정리의 명제
- 고칠 블록을 감싸는 상위 줄(예: `case app =>`, `have h : … := by`)
- 고칠 블록보다 앞에서 만든 `have`의 이름과 명제 목록(증명은 뺌). 모델이 이 자리에서 쓸 수 있는 사실을 알게 하려는 것임
- 직전 후보의 검증 피드백(현재 하네스와 같음)

모델은 고칠 블록의 새 내용만 내고, 하네스가 이를 원래 자리에 넣어 증명 전체로 검증함. 검증과 후보 선택은 현재 하네스와 같음.

### 조건

| 조건 | 모델에 보내는 증명 텍스트 | 모델이 내는 것 |
| --- | --- | --- |
| `whole` (기준선) | 증명 전체. 현재 하네스 그대로 | 증명 전체 |
| `local-r2` | 고칠 블록 + 앞뒤 형제 블록 2개씩 | 고칠 블록 |
| `local-r1` | 고칠 블록 + 앞뒤 형제 블록 1개씩 | 고칠 블록 |
| `local-r0` | 고칠 블록만 | 고칠 블록 |

모든 조건은 같은 모델, 같은 설정, 같은 예산 한도를 씀. `whole`에도 같은 예산을 주고 한도까지 재시도하게 함. 그래야 차이가 계산을 더 쓴 효과인지 근방의 효과인지 구분됨.

## 5. 예산과 기록

현재 main의 하네스는 `max_calls`로만 멈춤. 빌더님이 작업 중인 `codex/usage-cost-accounting` 브랜치(`b54afd4`, 미병합)의 `usage_cost.py`는 호출 기록의 비용을 합산하고 예산 대비 상태(`below_limit`·`exhausted`·`unknown`)와 남은 금액을 보고함. 다만 코드에 "observed_records_only; not a reservation or a hard cap on the next call"로 적혀 있듯, 이미 끝난 호출만 계산하며 다음 호출을 막지는 않음.

그래서 PR B에서는 별도 비용 계산을 만들지 않고, 이 집계 결과를 호출 전에 확인해 `exhausted`이면 멈추는 부분만 더함. 비교 실험에서 모든 조건이 같은 한도에서 멈춰야 같은 예산 비교가 되기 때문임.

실행마다 남길 값은 모두 이미 저장되는 `steps/NNN/` 기록에서 계산함.

| 값 | 출처 |
| --- | --- |
| 호출 수, 누적 비용 | `state.calls`, `state.cost_usd` |
| 호출별 입력·출력 토큰 | `response.json`의 `usage` |
| 컴파일 횟수, 결과 종류(통과, 증명 실패, 응답 거절) | `steps/NNN/evaluation/result.json`, `event.json` |
| 최종 토큰·heartbeat와 기준 대비 감소율 | `summary.json` |
| 종료 이유 | `summary.json`의 `stop_reason` |

입력 토큰을 따로 보는 이유는 1절의 관찰 때문임. 근방을 줄였을 때 입력 토큰이 얼마나 줄고, 그 대가로 성공률이 얼마나 떨어지는지가 이 실험의 핵심 결과임.

2문제 × 4조건 × 3번 × $0.5면 최대 $12임. 빌더님이 정하는 팀 한도 안에서 조정하며, 실제 사용 금액은 실행 후 기록으로 보고함. 빌더님 실행은 문맥이 약 32,000토큰인 문제 하나 기준이므로, 문제에 따라 호출당 비용은 달라질 수 있음.

## 7. 보고 방식

- 조정용과 held-out 결과를 섞지 않고 따로 적음.
- 조건마다 성공률, 감소율, 호출당 입력·출력 토큰, 문제당 비용을 문제별로 모두 적음. 3번 반복의 최솟값·최댓값도 적음.
- 감소율은 토큰과 heartbeat를 따로 적고, 하네스 선택 기준(두 비율의 합)도 함께 적음.
- minimal sufficient 근방은 "`whole`과 성공률·감소율 차이가 반복 간 변동보다 작은 가장 작은 r"로 판단하고, 판단 근거가 된 값을 함께 적음.
- 공식 Arena 점수가 아니라 팀 하네스의 측정값임을 표시함.

## 8. 빌더님께 확인할 것

main의 v1 하네스는 의존성 없는 Lean 프로젝트만 지원함. 빌더님께서 `codex/api-comparison-main-loop`에서 실제 웜업 문제 문맥으로 하네스를 돌려 주신 결과를 기준선으로 삼으면 비교가 가장 깔끔할 것 같음. 혹시 이 코드를 main에 반영하실 계획이 있으시면, 근방 조건도 그 구조에 맞춰 붙이겠음.

정리가 필요하시면 함께 돕겠음. 그 전까지는 1번 문제로 동작을 확인한 실험 스크립트로 근방 비교를 먼저 작게 돌려 보고, 결과를 공유하겠음.

정해 둔 것:

- 모델은 빌더님 실행과 같은 GPT-6.1 Sol을 써서 그 결과를 `whole` 기준선과 비교함.
- OpenRouter 키와 팀 한도는 실험 직전에 확인함.
