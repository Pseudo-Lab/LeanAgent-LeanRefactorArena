PR은 세 번에 나눠 올림.

### P02 반복 실행 (빌더님, 10/28)

웜업 2번(`CallElimCorrect.extractedOldExprInVars`)을 GPT-6.1 Sol·high로, 누적 API 비용이 $2.50에 도달할 때까지 반복함.

| 항목 | 값 |
| --- | --- |
| 호출 | 158회, $2.5019843, 약 118분 (호출당 약 $0.016) |
| 결과 | 222 → 120토큰, raw heartbeat 2,695,001 → 499,239 |
| 개선 시점 | 최종 개선의 80%를 6회차·$0.176에서 얻음. 마지막 개선은 124회차, 이후 34회·약 $0.365는 최선이 바뀌지 않음 |
| 사용량 | 입력 약 509만, 출력 약 13만 토큰. **입력의 94.3%가 캐시 읽기** |
| 실패 | 158개 후보 중 74개가 Lean 검증 실패. 사례로 현재 환경에 없는 보조정리 이름 사용(`List.append_subset_append`), 축약 중 타입 오류, 자동화 전술의 미해결 목표 |

같은 2번 문제의 팀 제출 증명(88.16점 묶음)은 19토큰임. 이 증명은 `fun_induction`과 라이브러리의 `List.Sublist` 생성자를 써서 증명 구조를 바꿨음. 88점 정리 문서도 큰 개선은 기존 일반 정리를 찾아 구조를 바꾼 데서 나왔다고 정리함.

### 이 결과가 설계에 주는 점

1. **입력 비용은 생각보다 작음.** 같은 문맥을 반복해 보내면 대부분 캐시로 처리됨. 따라서 보내는 문맥을 줄여 비용을 아끼는 효과는 작고, 매 호출 문맥이 바뀌면 캐시가 깨져 오히려 비싸질 수 있음.
2. **개선량의 차이는 탐색 방법에서 나옴.** 증명을 다시 쓰기만 하는 루프는 120토큰에서 멈췄고, 라이브러리 정리를 찾아 구조를 바꾼 탐색은 19토큰에 도달함.
3. **개선은 초반에 몰림.** 같은 방법으로 계속 호출하기보다, 개선이 멈추면 방법을 바꾸는 편이 예산을 잘 쓰는 것임.

그래서 이 실험은 비용을 줄이는 방법보다 **같은 예산에서 개선량을 늘리는 방법**을 비교함.

## 2. 참고한 점

1. **처음 보는 문제로 확인**: 하네스를 조정한 문제에서만 점수가 오르고 처음 보는 문제에서는 오르지 않는 경우가 많음(What Evolves When We Talk About Harness Evolution?). 수학 벤치마크 LiveMath에서는 학습용 35문제 중 21문제에 같은 정답 선지가 있어, 하네스가 그 지름길을 배움. 본 벤치마크 50문제는 처음 보는 문제이므로 조정에 쓰지 않은 문제로 따로 확인해야 함.
2. **같은 예산 기준선**: 새 하네스가 나아 보여도 재시도·검증·병렬 샘플로 계산을 더 쓴 효과일 수 있음. 기본 하네스에 같은 예산을 줘서 비교해야 함(같은 글의 budget-matched baseline). 대회는 재시도와 버린 후보까지 문제당 $3에 포함하므로 이 비교가 실제 점수와 같음.
3. **여러 번 시도**: 모델 출력은 실행마다 달라지므로 같은 조건을 여러 번(trial) 돌려야 함(Demystifying evals for AI agents).
4. **회귀 확인과 능력 확인 구분**: 이미 되던 문제가 여전히 되는지(regression)와 새 방식이 더 줄이는지(capability)는 따로 봄(같은 글).
5. **평가기는 루프 밖**: 하네스가 스스로 고칠 수 없는 곳에서 판정함. 현재 하네스는 이미 Lean 검증·공리 검사·선택을 모델 밖에서 하므로 그대로 유지함.

## 3. 문제 분리

웜업 15문제를 조정용 10문제와 held-out 5문제로 나눔. 출처마다 한 문제씩, 출처 안에서 두 번째 번호를 held-out으로 둠.

| 구분 | 문제 |
| --- | --- |
| 조정용 | 1, 3, 4, 6, 7, 9, 10, 12, 13, 15 |
| held-out | 2, 5, 8, 11, 14 |

- 프롬프트와 설정은 조정용 문제의 결과만 보고 바꿈.
- held-out 문제는 설정을 고정한 뒤 마지막에 한 번만 돌려 보고함. 1절의 P02 실행은 held-out 문제의 `whole` 기준선 참고값으로만 쓰고, 설정 조정에는 쓰지 않음.
- 본 벤치마크 공개 후에는 50문제 전체가 처음 보는 문제이므로, held-out 결과가 조정용 결과와 크게 다르면 그 설정은 조정용 문제에만 맞춘 것으로 봄.
- 한계: 블록 전략과 analyze의 유형 기준, 88점 제출의 탐색은 이미 15문제 전체를 반복해서 봤으므로 held-out이 완전히 깨끗하지는 않음.

## 4. 비교 조건

### 조건

| 조건 | 모델에 보내는 것 | 모델이 내는 것 | 확인할 것 |
| --- | --- | --- | --- |
| `whole` (기준선) | 현재 하네스 그대로 | 증명 전체 | |
| `whole+analyze` | `whole`과 같고, 요청 **끝에** analyze 결과를 덧붙임 | 증명 전체 | 고칠 위치와 유형 정보가 같은 예산의 개선량을 늘리는가 |
| `local-r1` (선택) | 고칠 블록과 같은 단계의 바로 앞뒤 블록 하나씩 | 고칠 블록 | 증명 일부만 보고도 같은 개선을 얻는가 |

모든 조건은 같은 모델, 같은 설정, 같은 예산 한도를 씀. `whole`에도 같은 예산을 주고 한도까지 재시도하게 함. 그래야 차이가 계산을 더 쓴 효과인지 조건의 효과인지 구분됨.

### `whole+analyze`

analyze 결과(유형, 고칠 후보 블록의 줄 범위, 중복 쌍과 서로 다른 토큰)를 요청 끝에 덧붙임. 앞부분을 바꾸지 않으므로 캐시를 그대로 쓸 수 있고, 모델이 내는 형식도 같아 하네스의 응답 처리를 바꾸지 않아도 됨. 1순위 비교 조건임.

### `local-r1`과 sufficient statistic

통계량 T(X)가 sufficient하다는 것은 T(X)만 알아도 데이터 X 전체를 아는 것과 모수 추정에 차이가 없다는 뜻임. 여기서 X는 증명 전체와 문맥, T는 고칠 블록과 그 주변임.

> T만 보낸 경우의 성공률과 감소율이 증명 전체를 보낸 경우와 차이가 없으면 T는 이 수정에 대해 sufficient하다고 봄.

다만 1절의 결과로 보면 큰 개선은 증명 전체의 구조를 바꾸는 데서 나왔으므로, 일부만 보내면 이런 개선을 찾기 어려울 수 있음. 또 매 호출 보내는 내용이 바뀌어 캐시 이득이 줄 수 있음. 그래서 `local-r1`은 예산이 남을 때 돌리는 선택 조건으로 둠. 진짜 sufficiency는 증명할 수 없으므로 실험 결과로 판단하는 근사임.

## 5. 예산과 기록

P02 실행은 누적 API 비용이 한도에 도달하면 멈추는 방식으로 돌았음. 비교 실험도 같은 방식으로 조건마다 같은 한도에서 멈춤. 비용 계산은 #29(`codex/usage-cost-accounting`, 미병합)의 기록을 그대로 쓰고 따로 만들지 않음.

실행마다 남길 값은 모두 이미 저장되는 `steps/NNN/` 기록에서 계산함.

| 값 | 출처 |
| --- | --- |
| 호출 수, 누적 비용 | `state.calls`, `state.cost_usd` |
| 호출별 새 입력·캐시 읽기·캐시 쓰기·출력·reasoning 토큰과 비용 | #29의 호출별 기록(`usage-cost.json`), 없으면 `response.json`의 `usage` |
| 컴파일 횟수, 결과 종류(통과, 증명 실패, 응답 거절) | `steps/NNN/evaluation/result.json`, `event.json` |
| 회차별 최선 후보의 토큰·heartbeat | `steps/NNN/event.json`의 `state_after.best` |
| 최종 토큰·heartbeat와 기준 대비 감소율 | `summary.json` |
| 종료 이유 | `summary.json`의 `stop_reason` |

회차별 최선 후보를 남기는 이유는 P02처럼 "누적 비용에 따라 최선이 어떻게 줄어드는가" 곡선을 조건마다 그리기 위함임. 같은 예산의 최종값뿐 아니라, 개선의 80%를 얼마의 비용에서 얻는지도 비교함.

## 6. 실행 규모 (제안)

| 항목 | 값 | 이유 |
| --- | --- | --- |
| 문제 | 조정용에서 라이브러리 1문제, PutnamBench 1문제 (예: 1번, 13번) | 문맥 크기가 다른 두 경우를 봄 |
| 조건 | `whole`, `whole+analyze` (예산이 남으면 `local-r1`) | 4절 |
| 반복 | 조건·문제마다 3번 | 모델 출력 변동 |
| 한도 | 실행 하나당 $0.5 | P02 기준 약 30회 호출. P02는 개선의 80%를 $0.176에서 얻음 |

2문제 × 2조건 × 3번 × $0.5면 최대 $6이고, `local-r1`을 더하면 최대 $9임. 팀 한도 안에서 조정하며, 실제 사용 금액은 실행 후 기록으로 보고함.

## 7. 보고 방식

- 조정용과 held-out 결과를 섞지 않고 따로 적음.
- 조건마다 성공률, 감소율, 호출당 새 입력·캐시 읽기·출력 토큰, 문제당 실제 청구 비용을 문제별로 모두 적음. 3번 반복의 최솟값·최댓값도 적음.
- 감소율은 토큰과 heartbeat를 따로 적고, 하네스 선택 기준(두 비율의 합)도 함께 적음.
- 조건마다 누적 비용–최선 곡선을 그림.
- 공식 Arena 점수가 아니라 팀 하네스의 측정값임을 표시함.

## 8. 진행 순서
