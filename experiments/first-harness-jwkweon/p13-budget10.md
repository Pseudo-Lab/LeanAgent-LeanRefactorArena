# P13 후보 예산 10회 · 독립 실행 2회

P13의 후보 제안 예산을 3회에서 10회로 늘려 새 서브에이전트 두 개로 실행한다.
기존 실행을 이어서 수리하지 않고 각각 원본에서 시작한다.
원본·소스·컴파일 문맥·평가식·Lean 버전·메모리 정책·검증 횟수는 이전 실험과 동일하게 유지한다.
프롬프트의 예산 안내만 `three`에서 `ten`으로 바꾸고 worker의 횟수 하드코딩을 설정값으로 대체했다.

## 고정 조건

- 실행 ID: `P13-10-r1`, `P13-10-r2`; 각각 `fork_turns=none`의 새 서브에이전트.
- 후보 제안 10회. 무효 후보도 횟수에 포함하며 11번째 제출은 거절한다.
- Lean v4.26.0, Mathlib `2df2f0150c275ad53cb3c90f7c98ec15a56a1a67`.
- 후보마다 일반 컴파일 1회와 계측 3회, 최종 선택 후보도 별도 재검증.
- 목적함수는 원본 대비 증명 토큰·raw heartbeat 비율의 평균이며 낮을수록 좋다.
- 문제·원본·기준 지표·현재 최선 후보·직전 후보와 피드백을 요청에 포함한다.
- 이전 실험의 후보와 팀 제출본은 solver 입력에 포함하지 않는다.
- 두 실행의 입력·작업 공간·임시 공간·응답·측정·상태·선택 결과를 분리한다.

## 비교 방법

1. 각 실행의 3·6·10번째 시점까지의 최선 후보를 비교한다.
2. 이전의 독립적인 3회 실험 결과도 함께 표시한다.
3. 현재 제출본은 solver와 분리된 `submission-control`에서 같은 로컬 Lean 환경으로 측정한다.
   제출본 측정 결과를 solver에게 피드백하지 않는다.
4. 완료한 실행은 전체 산출물 해시, 고정 입력, 요청과 이전 상태의 대응, 최종 후보와 검증 결과,
   기록 재생을 확인한다.

10회 실행의 첫 세 번은 모델이 전체 예산을 10회라고 알고 수행한 것이다.
따라서 같은 실행의 3회 checkpoint가 '전체 예산 3회' 실행과 동일한 반사실 실험은 아니다.
과거 두 실행과 이번 두 실행도 동일한 seed의 짝지어진 실험은 아니다.
독립 baseline 측정의 미세한 변동은 그대로 기록하고, 모델에 실제 전달된 요청을 보존한다.

## 범위와 기록

이 실험은 Codex 서브에이전트 어댑터를 사용한다. 후보 10번은 내부 모델 호출 10번이 아니다.
내부 호출 수·비용·정확한 모델 backend와 시스템 문맥은 관측하지 못하며 비용은 `null`로 기록한다.
실행 안의 에이전트 대화는 유지된다. 완전히 통제된 API 문맥 실험과 구분한다.
컴파일러·라이브러리는 읽기 전용 사용 정책으로 공유하며 OS 격리를 보장하지 않는다.

로컬 원문 기록: `runs/first-harness-jwkweon/p13-budget10-subagents-20261024/`.
`trial.json.max_proposals`가 예산의 단일 설정값이다.
예산 경계·조기 완료 거절·기존 3회 호환·재생을 포함한 테스트 21개를 통과한 worker를 각 실행에 복사했다.

## 실행 결과

두 에이전트 모두 후보를 정확히 10번 제출했다. 결과는
[p13-budget10-results.json](p13-budget10-results.json)에 보존한다.
**두 실행 모두 최종 재검증이 180초 제한으로 실패했다.** 아래 성능 수치는 최종 확정값이 아니라
탐색 중 일반 컴파일과 계측 3회를 통과했을 때의 선택 지표다. 실패 후 재시도하거나 제한을 바꾸지 않았다.

| 실행 | 3회차 최선 점수 | 6회차 최선 점수 | 10회차 최선 점수 | 3 → 10회차 점수 감소 |
| --- | --- | --- | --- | --- |
| P13-10-r1 | 0.17318 | 0.15148 | 0.14815 | 14.45% |
| P13-10-r2 | 0.15661 | 0.14323 | 0.10909 | 30.34% |

원본의 점수가 1이며 낮을수록 좋다. 각 시점까지 관측한 최선 후보를 비교한다.
추가 탐색은 두 실행 모두에서 개선을 만들었지만, 실행 간 선택된 코드와 성능은 달랐다.

| 후보 | 증명 토큰 | raw heartbeat 중앙값 | 로컬 점수 | 최종 재검증 |
| --- | --- | --- | --- | --- |
| [P13-10-r1 · 9회차 후보](results/p13-budget10/P13-10-r1.lean) | 451 | 4,783,343 | 0.14815 | 계측 3번째 실행 timeout |
| [P13-10-r2 · 8회차 후보](results/p13-budget10/P13-10-r2.lean) | 332 | 3,529,533 | 0.10909 | 일반 컴파일 timeout |
| 현재 제출본 · 별도 대조 측정 | 259 | 2,931,231 | 약 0.08588 | 일반 컴파일·계측 3회 통과 |

현재 제출본은 두 후보보다 토큰과 heartbeat 모두 좋다. 대조 측정은 같은 Mac과 고정된 Lean/Mathlib
환경에서 수행했으며 solver에게 제공하지 않았다. 표의 `.lean` 파일은 해당 문제의 고정 컴파일 문맥에서
사용하는 선언이며, 실험에서 선택한 파일과 바이트 및 SHA256이 같다.

참고로 과거 별도 3회 예산 실행의 점수는 0.13172와 0.19869였다.
이번 결과와는 독립적인 실행이므로 예산 증가의 일반적인 효과나 안정성을 통계적으로 입증하지 않는다.

## 검증 실패와 재현성 관측

- r1: 탐색 중 6개 후보가 검증됐고, 컴파일 오류 3회·timeout 1회였다.
  최종 선택 후보의 일반 컴파일은 91.53초, 계측 1·2회는 103.29초·166.45초로 통과했지만
  계측 3회가 180.21초에 종료됐다. 최종 중앙값은 `null`이다.
- r2: 탐색 중 7개 후보가 검증됐고, 컴파일 오류 1회·timeout 2회였다.
  최종 선택 후보의 일반 컴파일이 180.12초에 종료돼 최종 지표는 `null`이다.
- 두 실행의 산출물 해시·고정 입력·요청과 이전 상태의 대응·기록 재생은 모두 통과했다.
  기록 재생은 저장된 상태 전이를 다시 계산하는 검사이며 Lean을 재실행하는 검사가 아니다.
- 소프트웨어 환경 지문은 두 실행 모두 시작과 끝이 같았다. 원본 raw 중앙값은 각각
  115,674,908과 115,674,902였으며 이 값과 파생 순위 값 때문에 첫 실제 요청의 바이트는 달랐다.
- 시간 제한 실패의 원인은 확정하지 못했다. 호스트 부하·CPU 시간·절전/시계 관련 관측이 없으므로
  증명 자체의 비용 증가나 자원 경합 때문이라고 단정하지 않는다.

이번 기록은 탐색 성능, 최종 검증 성공 여부, 기록 무결성을 별도로 보고해야 한다는 사례다.
다음 실험에서는 제한 시간을 사전에 정하면서 컴파일·임포트 시간과 증명 계측 구간,
벽시계·CPU·메모리 관측을 함께 남겨 시간 제한 실패를 구분할 필요가 있다.
이 실험의 실패한 검증 결과와 봉인된 원본 기록은 그대로 보존한다.
