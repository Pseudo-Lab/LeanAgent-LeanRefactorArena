# 결과를 읽는 기준

8개 실행 완료 전에 작성했다. 코호트의 고정 조건은 `design.frozen.json`을 우선한다.
문제별로 A/B 각각 두 번을 실행하며 모델 seed를 맞춘 대응 표본은 아니다.

1. **주 결과:** 6회 후 선택한 유효 후보의 local cost 평균과 범위. 낮을수록 좋다.
   원본 대비 길이 비율과 raw HB 비율의 평균이다. 문제별 결과를 먼저 보고한다.
2. **탐색 과정:** 2·4·6회 누적 최선, 유효/실패/중복 제안 수.
   같은 코드의 재측정 흔들림을 개선으로 세지 않는다.
3. **전략 사용:** B의 family 기록과 비최선 부모 참조. 부모 참조는 solver가 적은
   메타데이터이고 실제 코드 계보의 자동 증명이 아니다. 사용 빈도만으로 효과를 주장하지 않는다.
4. **비용 교환:** 길이와 HB를 따로 본다. HB만 좋아진 후보를 종합 우승으로 부르지 않는다.
   요청 bytes와 Lean 작업 수·시간도 제시한다. 후보 기회가 같아도 모델 계산량이나
   실제 평가 시간은 같지 않다. 정확한 모델 토큰·비용은 관측할 수 없다.
5. **선택 안정성:** 선택 시 중앙값과 마지막 fresh 재검증 중앙값의 차이를 보고한다.
   raw HB 변동이 1%를 넘으면 별도 검토 표시하되 임의로 표본을 빼거나 재시도하지 않는다.
6. **근거 검사:** frozen inputs/code, 원문과 계측 source의 정확한 대응, fresh nonce,
   target 공리, 최종 유효성, replay, 공유 runtime 전후 hash, 독립 agent dispatch 순서를 검사한다.

유효 후보 수가 늘면서 cost도 좋아지면 실용적인 신호지만 인과 원인을 하나로 좁힐 수 없다.
B가 좋아져도 프롬프트·단계 지침·부모 기억 중 무엇 때문인지는 다음 ablation이 필요하다.
B가 나빠지면 구조 지침의 과도한 제한, 추가 schema 오류, 분기 탐색의 예산 부족을
실제 기록에서 구분한다. 이번 두 문제는 이전 개발에 사용했으므로 일반화 결론을 내리지 않는다.

공식 LB 점수는 계산하지 않는다. 전 버전 호환성 및 공식 worker를 실행하지 않았기 때문이다.
후속 실험은 새로운 문제를 고정해 더 많은 독립 반복을 실행하고, 이 묶음에서 기능을
하나씩 제거해 어떤 요소가 필요한지 검증하는 방식이 적합하다.
