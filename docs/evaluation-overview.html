01 / TWO SCENARIOS

실험 중에도, 실험이 끝난 뒤에도.

생성 모델이나 리팩터링 전략과 독립적으로,
같은 평가 코드가 두 시나리오를 담당합니다.

DURING EXPERIMENTCheckpoint

중간 결과마다 평가

원본의 기준값을 먼저 측정합니다. 이후 에이전트가 후보를 반환할 때마다 검증과 측정을 완료하고, 결과를 다음 시도에 전달합니다.

  • 증명 토큰 수와 heartbeat 측정
  • 컴파일 오류와 점수를 다음 시도의 피드백으로 제공
  • 평가·기록 완료 후에만 다음 agent 호출 진행
AFTER EXPERIMENTFinal selection

최종 후보 자동 선정

원본과 기록된 모든 후보를 지정 환경에서 다시 평가합니다. 검증과 정책을 통과한 후보 중 가장 높은 점수의 코드를 최종 결과로 내보냅니다.

  • 모든 지정 환경에서 재검증
  • 기본 3회 독립 측정 후 중앙값으로 비교
  • 개선이 없으면 재검증된 원본 유지

02 / EVALUATION LOOP

제안은 agent가, 평가와 선택은 코드가.

측정 기준과 환경은 실행 시작 시 고정합니다.
후보의 점수는 하네스가 직접 계산합니다.

  1. 01

    문제 입력

    명제·원본 증명
    Lean 환경·평가 정책

  2. 02

    원본 측정

    기준 token·heartbeat
    초기 검증 성공 확인

  3. 03

    후보 생성

    API / agent 호출
    중간 산출물 반환

  4. 04

    검증·측정

    명제·컴파일·공리 확인
    token·heartbeat 측정

  5. 05

    기록·피드백

    오류·점수·부모 저장
    개선 채택 또는 수정

  6. 06

    최종 선택

    모든 후보 재평가
    최고점 코드 내보내기

↶ 후보 생성 → 평가 → 피드백 반복
평가가 다음 시도의 필수 단계입니다. run_search()는 후보의 측정과 저장을 마친 뒤 다음 propose()를 호출합니다. 측정할 중간 산출물마다 한 번 반환하도록 adapter를 구성합니다.

03 / SCORING & SELECTION

검증된 후보 중, 가장 높은 점수.

평가 기준은 실행 시작 시 고정합니다.
원본은 0점, 높은 점수일수록 좋은 후보입니다.

기본 점수 = 토큰 감소율 × 0.5 + heartbeat 감소율 × 0.5

  • 모든 지정 환경의 검증과 설정된 정책을 통과한 후보만 비교합니다.
  • 최고점 후보를 선택하며, 동점이면 먼저 기록된 후보를 유지합니다.
  • 개선이 없으면 재검증된 원본을 유지하고, 원본 검증도 실패하면 선택하지 않습니다.

감소율은 % 기준입니다. 가중치와 최소 개선폭은 실행 설정에서 지정할 수 있습니다. 이 점수는 로컬 실험용이며 공식 Arena 점수가 아닙니다.

05 / INTEGRATION CONTRACT

전략은 자유롭게. 평가 접점은 하나로.

API / agent 담당자는 propose(feedback)에
생성 로직을 연결하면 됩니다.

후보와 선택 근거를 함께 보존

코드, 부모 후보, SHA-256, 측정 로그, 오류와 점수를 하나의 실행 기록으로 연결합니다. 중단된 평가는 미완료로 남기고 후속 선택을 차단합니다.

run/ ├─ manifest.json ├─ candidates/ │ ├─ baseline.lean │ └─ candidate-0001.lean ├─ evaluations/ │ └─ 입력 코드 · 측정 로그 └─ selections/final-001/ ├─ selected.lean └─ selection.json

현재 확정 결과는 manifest.json.selection이 가리킵니다.
새 후보를 추가하면 이전 선택을 해제하고 다시 최종 평가합니다.

PYTHON · MODEL-NEUTRAL INTERFACE
from refactor_eval.session import Session, run_search

session = Session("runs/experiment-001")
session.initialize("problem.json")

def propose(feedback):
    # API / agent의 생성 로직 연결
    code = your_agent(feedback)
    if code is None:
        return None  # 탐색 종료 → 최종 평가
    return {
        "code": code,
        "parent_id": feedback["incumbent_id"],
        "note": "이번 시도의 변경 의도",
    }

selection = run_search(
    session, propose, max_attempts=20
)

feedback에는 명제·원본 측정값·현재 최선의 코드·직전 후보의 평가 결과가 들어갑니다. 후보 코드는 명제를 보존한 := by 형식의 전체 선언입니다.

바로 실행할 수 있는 오프라인 예제저장소 루트에서 실행

TERMINAL · NO MODEL / API CALLS
python3 -m refactor_eval run \
  --problem examples/basic/problem.json \
  --run-dir runs/demo \
  --max-attempts 3 \
  -- python3 examples/replay_agent.py

Python 3.10+와 사전 설치된 Lean 4.26.0이 필요합니다. 외부 Python 패키지 없이 실행하며, 재실행 시에는 새 --run-dir을 지정합니다.

현재 구현의 보장 범위와 확인한 환경
  • 측정 강제 범위: 하네스에 반환한 중간 산출물입니다. 에이전트 내부에서 반환하지 않은 임시 결과까지 감시하지는 않습니다. skill은 호출 절차를 안내하고, run_search()가 실제 반복 순서를 제어합니다.
  • 측정 의미: token은 모델의 BPE 토큰이나 proof term 크기가 아닌 증명 소스의 lexical token입니다. heartbeat는 대상 선언을 동기 elaboration하며 측정한 raw 값을 1,000으로 나눈 정수값입니다.
  • 검증 범위: 실제 Lean 통합 검증은 4.26.0에서 수행했습니다. 다중 환경 선택 로직은 테스트로 확인했지만, 전체 Arena 지정 버전을 모두 실행한 것은 아닙니다.
  • 담당 경계: 유료 API 호출·재시도·예산 관리는 adapter 담당 범위이며, 실제 생성 agent와의 연결은 이번 검증에 포함하지 않았습니다.
