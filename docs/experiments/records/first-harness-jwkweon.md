### Lean 리팩터링 하네스 실험 참고

기준일: 2026년 10월 25일 KST
실험 브랜치: `exp/first-harness-jwkweon`

대회용 Lean 리팩터링 에이전트의 실험을 일관되게 수행하기 위해 최소 하네스를 만들고, 독립 반복, 후보 예산, 프롬프트 지침, 오류 피드백 정책을 차례로 비교했다. 팀 공유와 PPT 작성 시 실험 단위와 비교 조건을 확인하기 위한 참고 자료다.

실제 solver 실험은 **34개 독립 실행과 312개 후보 제출**이다. 최종 선택본은 32개 실행에서 재검증을 통과했고, 초기 P13 예산 확장 실험의 두 실행은 최종 검증에서 timeout으로 실패했다. 조건당 두 번의 탐색이므로 결과는 문제별 관측으로 해석한다. 프롬프트와 구조화 피드백의 효과는 두 문제에서 일관되지 않았다.

#### 실험의 진행 순서

```text
최소 하네스 구축과 동작 검증
    → P01과 P13을 각각 두 번 독립 실행
    → P13의 후보 예산을 3회에서 10회로 확대
    → P13과 P01에서 프롬프트 지침별 비교
    → 두 문제에서 오류 피드백 정책 비교
```

| 실험 | 문제 | 비교 조건 | 반복 | 실행당 후보 예산 | 독립 실행 수 | 후보 제출 수 |
|---|---|---|---|---:|---:|---:|
| 초기 반복 | P01·P13 | naive 프롬프트 | 문제당 2번 | 3회 | 4 | 12 |
| 예산 확장 | P13 | naive 프롬프트, 10회 예산 | 2번 | 10회 | 2 | 20 |
| 프롬프트 비교 | P13 | A·B1·B2·B3·B4 | 조건당 2번 | 10회 | 10 | 100 |
| 동일 프롬프트 비교 | P01 | A·B1·B2·B3·B4 | 조건당 2번 | 10회 | 10 | 100 |
| 오류 피드백 비교 | P01·P13 | L 기존·S 구조화 | 문제와 조건별 2번 | 10회 | 8 | 80 |
| 합계 | | | | | **34** | **312** |

하네스 구축 시 수행한 고정 응답 smoke test와 기존 제출본의 별도 대조 측정은 위 solver 집계에 포함하지 않았다. Smoke test는 미리 정한 응답을 실제 Lean으로 검증한 기능 검사이며 모델의 풀이 성능을 측정한 실험이 아니다.

P01은 Strata의 `CallElimCorrect.substOldPostSubset`으로, 특정 치환 후의 변수 집합이 원래 변수들과 지정한 변수 안에 포함됨을 보이는 정리다. P13은 `putnam_1964_a4`로, 주어진 점화식을 따르는 유계 정수 수열이 어느 시점부터 주기적임을 보이는 문제다. 정확한 명제는 [P01 입력](https://github.com/Pseudo-Lab/LeanAgent-LeanRefactorArena/blob/3ee67de1707d712321e403da5cf1d064dc4240f9/experiments/first-harness-jwkweon/feedback-ablation-v1/inputs/P01/problem.json)과 [P13 입력](https://github.com/Pseudo-Lab/LeanAgent-LeanRefactorArena/blob/3ee67de1707d712321e403da5cf1d064dc4240f9/experiments/first-harness-jwkweon/feedback-ablation-v1/inputs/P13/problem.json)에 보존한다.

#### 실행과 후보와 컴파일의 차이

| 용어 | 의미 |
|---|---|
| 독립 실행 또는 run | 새 에이전트가 원본에서 시작해 정해진 후보 예산을 사용하고, 최종 선택과 재검증까지 수행하는 실험 한 번 |
| 후보 또는 proposal | 실행 안에서 제출한 완성된 증명 본문 하나. 실패하거나 이전 증명을 다시 제출해도 1회로 계산 |
| 모델 호출 | 에이전트 내부의 모델 처리. 후보 제출 수와 같다고 가정하지 않으며 이번 어댑터에서는 횟수를 관측하지 못함 |
| 일반 컴파일 | 원래 컴파일 문맥에 후보를 넣어 검증하는 Lean 실행 |
| 계측 컴파일 | 같은 후보의 대상 선언 처리 전후 heartbeat를 측정하는 Lean 실행 |
| checkpoint | 한 실행의 해당 회차까지 찾은 최선 후보를 관측하는 시점 |
| 최종 검증 | 탐색이 끝난 뒤 선택본을 별도로 일반 컴파일하고 다시 계측하는 절차 |
| 기록 replay | 저장된 요청·응답·검증 결과로 상태 전이와 선택을 다시 계산하는 검사. 모델이나 Lean을 새로 실행하지 않음 |

예를 들어 에이전트 두 개가 각각 후보 10개를 제출하면 **2개 실행·20개 후보 제출**이다. 서로 다른 증명이 20개라는 뜻은 아니다.

#### 한 실행의 파이프라인

```text
고정 입력과 코드 스냅샷 준비
    ↓
원본 검증과 기준 지표 준비
    ↓
모델이 완성된 증명 본문 하나 제출
    ↓
하네스가 응답 형식과 생성 제약 검사
    ↓
원래 문맥에서 일반 컴파일 1회
    ↓ 통과
같은 후보를 새 Lean 프로세스에서 계측 컴파일 3회
    ↓
유효성·비용·최선 후보·직전 후보·피드백 기록
    ↓
다음 후보 생성 요청 → 예산까지 반복
    ↓
선택본 별도 재검증 → 산출물 해시 봉인 → 기록 replay
```

실패하면 피드백을 기록하고 다음 후보로 넘어간다. 일반 컴파일에서 실패한 후보는 뒤의 계측을 수행하지 않는다. 유효한 후보 하나에는 최대 4번의 컴파일이 필요하므로, 후보 10개가 모두 유효하면 후보 검증에만 40번 컴파일한다. 원본 준비와 최종 검증은 별도다. 후속 실험의 원본 준비는 실행별 중복 측정 대신 문제별 준비 단계에서 수행했다.

계측 3회는 같은 후보를 반복 측정하는 절차다. 새 후보나 모델 응답을 세 번 생성하지 않는다. 측정값의 미세한 변동을 관측하고 중앙값을 사용하기 위해 정한 반복 수이며 Lean의 필수 규칙은 아니다.

계측 코드는 `IO.getNumHeartbeats`를 대상 선언 처리 직전과 직후에 읽어 차이를 구한다. 계측 시 대상 선언의 비동기 elaboration을 끄고 선언 처리가 끝난 뒤 값을 읽는다. 먼저 원래 문맥으로 일반 컴파일을 수행해, 계측용 추가 import가 후보의 오류를 가리는 것을 방지한다. 구현은 [evaluator/lean.py](https://github.com/Pseudo-Lab/LeanAgent-LeanRefactorArena/blob/3ee67de1707d712321e403da5cf1d064dc4240f9/experiments/first-harness-jwkweon/evaluator/lean.py)에 있다.

매 요청에는 문제·원본·기준 지표·현재 최선 `best`·직전 후보 `latest`와 피드백·현재 회차·전체 예산을 넣는다. 후보와 지표, best/latest, 남은 예산은 실행 중 바뀌며 이 상태를 구성하고 선택하는 규칙은 고정한다.

**하네스의 요청 구조와 에이전트 자체의 기억은 구분한다.** 각 실행은 부모 대화를 넘기지 않은 새 서브에이전트에서 시작하지만, 실행 안의 에이전트 대화는 유지된다. 매 단계 완전히 통제된 API 문맥만 전달한 실험은 아니다. 정확한 backend 모델 ID·sampling seed·숨겨진 시스템 문맥·내부 호출 수·요금은 관측하거나 고정하지 못했다. OpenRouter를 호출한 실험도 아니다.

파일 접근 범위는 지침으로 제한했으며 OS 수준의 파일·네트워크 격리를 구현하지 않았다. 같은 호스트에서 병렬 실행하므로 자원도 공유한다.

#### 평가 지표와 컴파일 옵션

비용은 원본 대비 증명 토큰과 raw heartbeat 비율의 평균이다.

```text
비용 = 0.5 × (후보 증명 토큰 / 원본 증명 토큰
             + 후보 raw HB / 원본 raw HB)
```

원본 비용은 1이고 낮을수록 좋다. 증명 토큰은 모델의 과금 토큰이 아니며 이 비용은 로컬 실험 지표다. 실제 선택은 부동소수점 오차를 피하도록 공통 분모를 제외한 정수 분자로 비교한다.

raw HB는 메모리 할당에 기반한 Lean의 작업량 카운터다. 초 단위 경과 시간이 아니다. 계측에서 기록한 raw 값과 Lean의 사용자용 heartbeat 수치 사이에는 1,000배 단위 차이가 있다. 이번 점수는 계측 3회의 **raw 값 중앙값**을 사용한다. [Lean 4.26 heartbeat 구현](https://raw.githubusercontent.com/leanprover/lean4/v4.26.0/src/Lean/Util/Heartbeats.lean)

| 설정 | 의미 |
|---|---|
| `-j1` | `--threads=1`. Lean 파일 처리 스레드 수 설정. 에이전트 병렬도와 별개 |
| `-M4096` | `--memory=4096`. Lean의 메모리 상한 설정, 단위 MB |
| `-T200000` | `--timeout=200000`. task별 메모리 할당량에 기반한 결정적 작업량 제한. 초 단위 시간이 아님 |
| 하네스의 180초 또는 420초 | Python이 적용하는 Lean 호출별 실제 경과 시간 제한. 넘으면 프로세스 그룹 종료 |

옵션 의미는 실험에 사용한 Lean 4.26 실행 파일의 `--help`로 확인했다. 실제 시간 제한은 프로세스 시작, import, 문맥 처리까지 포함한다. HB 계측은 그중 대상 선언 구간을 측정한다. 따라서 낮은 HB가 짧은 전체 컴파일 시간을 보장하지 않는다.

프롬프트와 피드백 실험에서 모델 요청과 점수 분모에 사용한 공통 원본 기준값은 다음과 같다.

| 문제 | 원본 증명 토큰 | 원본 raw HB |
|---|---:|---:|
| P01 | 313 | 5,173,306 |
| P13 | 1,769 | 115,674,908 |

#### 실험 사이에 달라진 조건

| 항목 | 초기 반복과 P13 예산 확장 | 프롬프트와 피드백 비교 |
|---|---|---|
| 원본 기준값 | 실행별 원본 재측정값을 요청에 포함 | 문제별 기준값을 공통 고정. 준비 단계 재측정은 별도 관측으로 보존 |
| 첫 요청 | 문제·프롬프트가 같아도 기준 지표 차이로 바이트가 다름 | 프롬프트 실험은 같은 문제·조건 내 동일. 피드백 실험은 같은 문제의 네 실행 모두 동일 |
| Lean 시간 제한 | 호출별 180초 | 호출별 420초 |
| solver 병렬도 | 초기 반복 최대 3개, 예산 확장 최대 2개 | 최대 2개. 완료 순서대로 다음 독립 실행 배정 |

따라서 각 실험 묶음 안의 대조군을 우선 비교한다. 서로 다른 묶음의 naive A 결과를 모델 변동만 다른 동일 조건 반복으로 바로 합치지 않는다.

모든 10회 실행은 처음부터 전체 예산이 10회임을 알고 진행했다. 3·6·10회는 한 실행의 누적 최선 관측이다. 10회 실행의 3회 checkpoint와 처음부터 3회 예산을 알려준 실행은 동일한 조건이 아니다.

#### 프롬프트 비교 조건

A는 명제 보존, 출력 형식, 접근 제약, 검증 주체, 로컬 비용 최소화를 안내하는 naive 프롬프트다. 무지시 조건을 뜻하지 않는다. [A 원문](https://github.com/Pseudo-Lab/LeanAgent-LeanRefactorArena/blob/3ee67de1707d712321e403da5cf1d064dc4240f9/experiments/first-harness-jwkweon/prompt-ablation-v1/prompts/A.txt)

B1부터 B4까지는 각각 A에 지침 하나를 추가한 별도 조건이다. 지침을 누적하지 않았다. 모든 조건에서 오류 피드백은 기존 L 방식이고 후보 예산은 10회다.

| 조건 | 추가한 지침 |
|---|---|
| B1 | 더 강한 지역 불변식, 재귀에 맞는 귀납, 상위 보조정리 등 구조적 대안을 검토 |
| B2 | 전체 지역 문맥을 반복 단순화하는 대신 관련 사실로 목표만 단순화하는 방법을 검토 |
| B3 | 다른 구조를 탐색했다면 다음 후보 한 번을 집중 수리·개선에 사용하는 방법을 검토. 구조 변경당 후속 시도 최대 한 번이며 일반 예산 소비 |
| B4 | 큰 중간 결과를 먼저 만들기보다 `apply`·`refine`·`exact`로 목표에서 사용 가능한 보조정리를 역방향 적용하는 방법을 검토 |

주 관측 시점은 10회차, 보조 관측 시점은 3·6회차다. 다른 개발 세션에서 도출한 전략 가설을 시험했으며 Astra와 다른 모델의 통제된 성능 비교는 수행하지 않았다.

#### 오류 피드백 비교 조건

이 실험은 naive A 프롬프트를 고정하고, **실패한 Lean 컴파일의 오류를 선택하고 전달하는 정책**만 L과 S로 나눴다. 성공, 응답 형식 거절, 컴파일 오류 이외의 실패 피드백은 기존과 동일하다. 추가 Lean 호출, 라이브러리 탐색, 수리 전략, 후보 예산을 제공하지 않았다.

##### 기존 L 방식

```text
전체 로그를 파일로 저장
    → 평가 결과에는 로그 끝 4,000자 포함
    → 오류 정보 직렬화
    → details 앞 1,600자 전달
```

길이를 기준으로 자르므로 긴 가정과 타입 정보가 뒤를 차지하면 첫 오류의 제목이 사라질 수 있다. 직렬화한 문자열 자체도 잘릴 수 있다.

##### 구조화 S 방식

```text
같은 검증에서 저장한 전체 로그
    → 첫 실제 오류 탐색
    → 위치·메시지·case·목표·주변 가정 추출
    → 필드별 제한 적용
    → 전체 1,600자 안의 완전한 JSON 문자열 전달
```

| 필드 | 의미 | 제한 |
|---|---|---|
| `location` | 오류 위치 | 220자 |
| `message` | 첫 오류 메시지 | 1,100자 |
| `case` | 증명 분기 | 120자 |
| `goal` | 해당 목표 | 500자 |
| `local_context` | 목표 주변의 지역 가정 | 마지막 12줄, 최대 650자 |
| `truncated` | 정보가 잘렸는지 표시 | 참 또는 거짓 |

**1,600자는 전체 프롬프트나 모델의 문맥 창 크기가 아니라 `feedback.details`의 문자 상한**이다. 필드 값부터 줄여 JSON 구조를 유지한다. 첫 오류만 선택하므로 나머지 오류가 모두 전달되는 것은 아니다.

S는 코드로 수행한 구조화 추출과 기계적 절단이다. 모델이 관련성을 판단해 의미를 요약하거나 수리 전략을 제안하지 않았다. 따라서 이번 독립변수에는 **정보 선택과 구조화가 함께 포함**되며 JSON 형식만의 효과를 분리하지 않는다. 구현은 [error_feedback.py](https://github.com/Pseudo-Lab/LeanAgent-LeanRefactorArena/blob/3ee67de1707d712321e403da5cf1d064dc4240f9/experiments/first-harness-jwkweon/feedback-ablation-v1/error_feedback.py)에 있다.

주 관측값은 문제·조건별로 3회차까지 원본보다 낮은 비용을 찾은 실행 수다. 초기 유효 후보 수, 최초 유효·개선 회차, 3·6·10회 비용, 실제 오류 피드백 노출 횟수, 최종 검증도 함께 기록했다. 3회차에서 처음 난 오류의 피드백은 4회차부터 사용할 수 있으므로 3회차 성과에 대한 노출로 세지 않는다.

##### 정보량에 대한 사후 확인

S의 컴파일 오류 피드백은 총 8건이었다. 길이는 164~1,240자로 모두 전체 상한보다 짧았지만, 그중 3건은 필드별 제한이나 가정 줄 수 제한으로 정보가 잘렸다. 저장된 동일 로그에 대해 전체 상한만 1,600자에서 6,400자로 바꾸어 다시 추출해도 8건 모두 기존 출력과 같았다.

이 확인은 저장된 로그의 포맷터를 다시 계산한 검사다. 새 solver나 Lean 검증을 실행하지 않았으며 위 34개 실행·312개 후보에 추가되는 실험이 아니다. 피드백 정보량의 성능 효과는 아직 검증하지 않았다. 현재 코드에서는 총상한만 늘려도 내부 제한이 먼저 작동할 수 있다.

| P13 | S | 2/2 | 2.0/3 | 0.189825 | 0.147987 | 0.140107 |

10회 평균 비용은 S가 L보다 P01에서 14.23% 낮고 P13에서 17.41% 높았다. 이 표본에서 구조화 정책의 일관된 성능 향상은 관측하지 못했다. 유효 후보는 63/80, 컴파일 오류는 17/80이었으며 선택본 8개 모두 최종 검증과 기록 replay를 통과했다.

P13의 L 두 실행은 3회차 전에 오류 피드백을 받지 않았고 S 두 실행은 각각 한 번 받았다. 같은 첫 요청에서도 응답부터 경로가 갈라졌으므로 초기 차이를 피드백의 인과효과로 단정할 수 없다.

#### 최종 timeout에서 확인한 사실

Timeout은 초기 P13 예산 확장 두 실행의 최종 검증에서 발생했다. 두 후보는 탐색 중 일반 컴파일과 계측 3회를 통과했지만 별도 최종 검증에서 180초 제한을 넘었다.

| 실행 | 최종 검증 관측 |
|---|---|
| P13-10-r1 | 일반 컴파일 91.53초, 계측 1회차 103.29초, 2회차 166.45초는 통과. 3회차가 180.21초에 종료 |
| P13-10-r2 | 일반 컴파일이 180.12초에 종료 |

확인된 것은 하네스의 실제 경과 시간 제한에 따른 종료이며, Lean의 `-T` 상한에 도달했다는 기록은 아니다. 당시에는 호스트 부하, CPU 시간, I/O, 절전 관련 관측이 없어 원인을 특정하지 못했다. r1의 통과한 최종 계측 두 번은 raw HB가 4,783,355와 4,783,340으로 비슷했지만 경과 시간은 크게 달랐다.

후속 실험은 시작 전에 제한을 420초로 정했다. 이전 실패를 조건 변경 후 재시도하지 않았고 봉인된 실패 기록을 유지했다. 최종 검증 성공, 탐색 중 비용, 기록 무결성은 각각 보고한다.

#### 재현성 확인과 해석 범위

입력·실행 코드·생성 소스·로그의 해시, 요청과 이전 상태의 대응, 선택 결과, 기록 replay를 확인했다. 프롬프트 실험과 피드백 실험에서는 공유 런타임의 실험 전후 해시도 일치했다. 대상 파일은 P01이 11,532개, P13이 95,212개였다.

피드백 실험의 P01-L-r1과 P13-S-r1은 계정 사용량 제한으로 중단된 뒤 사용자의 재개 지시에 따라 같은 solver 문맥에서 이어갔다. 재개 시 진행 중인 검증은 없었고 완료 후보 재시도나 예산 추가도 없었다. P01 프롬프트 실험에서는 후보 4의 응답 경로 오타 한 건을 검증 시작 전에 고쳤으며 후보 수나 검증 횟수는 늘리지 않았다.

해시 일치와 replay는 기록의 일관성을 보여주지만 모델이 같은 증명을 다시 생성함을 보장하지 않는다. 조건당 두 실행이고 두 문제 모두 개발에 사용했으므로 통계적 우위나 미지의 문제에 대한 일반화를 입증하지 않는다.

#### 미실시 가설과 다음 비교안

**의미를 보존하는 오류 피드백 요약은 아직 실험하지 않았다.** 현재 S는 구조화 추출과 기계적 절단이며 관련성을 판단하는 요약이 아니다. 다음은 후속 실험안이다.

| 확인할 질문 | 비교안 | 고정할 조건 |
|---|---|---|
| 피드백 정보량을 늘리면 개선되는가 | 공통 추출 규칙에서 총예산 1,600자와 6,400자 비교 | 같은 A 프롬프트, 후보 예산, 측정·선택 규칙. 필드별 선행 제한이 예산 차이를 무효화하지 않도록 두 조건 공통으로 설계 |
| 의미를 보존한 요약이 추출보다 도움이 되는가 | 구조화 추출과 의미 기반 요약 비교 | 원문 로그, 이용 가능한 정보, 총 피드백 예산, solver 프롬프트, 후보 예산 |

요약에서는 오류 설명을 간결하게 하되 필요한 목표 수식과 가정은 원문을 보존한다. 규칙 기반이라면 정규화와 중복 제거를 고정하기 쉽다. 모델 기반이라면 요약 모델, 프롬프트, 생성 설정, 입력, 출력, 호출 수, 관측 가능한 비용도 기록한다. 요약에 수리 전략이나 새 증명 제안을 포함하면 또 다른 개입이 되므로 비교 범위를 먼저 정한다.

후보 예산, 개별 프롬프트 지침, 오류 피드백 정책은 실험했지만, 피드백 정보량 자체, 의미 기반 요약, 메모리 정책, 라이브러리 검색 허용, 모델 종류는 독립변수로 실험하지 않았다.

#### 공유 자료에 사용할 표기

- 표와 그래프에 문제, 조건, 반복 수, 관측 회차, 비용은 낮을수록 좋다는 점을 표시한다.
- 평균과 실행 간 범위를 함께 보여준다. 실행별 수치와 선택 증명은 각 결과 문서에서 확인한다.
- 실행 수, 후보 제출 수, 모델 호출 수, 컴파일 횟수를 구분한다.
- 증명 유효성, 비용 개선, 최종 검증 성공을 구분한다.
- 1,600자는 오류 피드백 `details`의 상한이며 전체 프롬프트의 상한으로 표기하지 않는다.
- 요약의 효과, 예산 증가의 일반적인 효과, timeout의 원인을 확정된 결론으로 표현하지 않는다.
